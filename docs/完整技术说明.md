# 企业级 AI Agent 平台完整技术说明

> 日期：2026-07-29  
> 版本：0.1（Architecture Baseline）  
> 依据：用户提供的 ChatGPT 分享内容  
> 文档性质：首版技术规格；开放问题确认后持续更新

## 1. Objective

建设一个企业级 AI Agent 开发、运行与治理平台，使研发团队可以通过统一界面和 API：

- 配置模型、Prompt、工具、知识库、记忆和工作流；
- 调试、评测、版本化并发布 Agent；
- 以同步、SSE 或异步任务方式调用 Agent；
- 对运行过程执行权限校验、人工审批、审计和成本控制；
- 通过 Trace、指标、反馈与测试集持续改进质量。

平台不负责训练基础模型，竞争力集中在 Agent Runtime、上下文工程、工具生态、RAG、评测与企业工程化。

## 2. Architecture

```text
Browser / Business System
          |
    API Gateway / Auth
          |
  Control Plane (FastAPI)
   |      |       |       |
Agent   Model   Tool    Knowledge
Config  Gateway Registry Pipeline
   \      |       |       /
        Agent Runtime
   State / Checkpoint / Approval
          |
  Worker & Async Job Queue
          |
PostgreSQL Redis Qdrant MinIO
          |
Trace / Metrics / Logs / Eval
```

系统分为四层：

1. **体验层**：管理控制台、Playground、公开 API 和 SDK。
2. **控制面**：租户、Agent 定义、版本、模型、工具、知识库、评测和发布管理。
3. **运行面**：Agent 状态机、模型调用、工具执行、RAG、记忆、审批、中断恢复。
4. **数据与治理层**：关系数据、缓存/队列、向量、对象文件、Trace、指标、审计和密钥。

## 3. Tech Stack

| 层 | 首选 | 说明 |
|---|---|---|
| Web | Vue 3、TypeScript、Vite | 适合现有前端能力，控制台与 Playground |
| API | Python 3.11+、FastAPI、Pydantic | 类型明确，AI 生态成熟，自动生成 OpenAPI |
| Agent Runtime | LangGraph | 显式状态、Checkpoint、分支、循环和人工介入 |
| 模型适配 | 自有 Model Gateway 接口 | 隔离 OpenAI、Anthropic、DeepSeek、Qwen 等差异 |
| 关系库 | PostgreSQL | 元数据、版本、权限、运行索引、审计 |
| 缓存/队列 | Redis | 限流、短期状态、事件广播；任务队列实现后选 |
| 向量库 | Qdrant | 文档向量和带过滤条件的语义检索 |
| 对象存储 | MinIO/S3 | 原始文档、解析产物、大型运行附件 |
| 观测 | OpenTelemetry + 可插拔后端 | Trace、Metrics、Logs 使用统一语义 |
| 部署 | Docker Compose → Kubernetes | 本地先可运行，生产再按负载扩容 |

外部框架只存在于适配器层。领域模型、权限和审计不能直接依赖某个模型供应商或 Agent 框架。

## 4. Domain Model

### 4.1 核心实体

- `Tenant`：租户与资源隔离边界。
- `User` / `ServiceAccount`：人类成员与机器调用方。
- `Role` / `Policy`：RBAC 基础角色和资源级策略。
- `Agent`：稳定业务身份。
- `AgentVersion`：不可变配置快照，包含模型、Prompt、工具、知识库和工作流。
- `Deployment`：环境到 AgentVersion 的发布映射。
- `Thread`：一次持续对话或任务上下文。
- `Run`：一次 Agent 执行。
- `RunStep`：模型、工具、检索、审批等原子步骤。
- `ToolDefinition`：工具 Schema、执行方式、风险级别和权限。
- `ToolCredential`：加密后的租户级或用户级凭证引用。
- `KnowledgeBase` / `Document` / `Chunk`：知识库、源文件和检索片段。
- `MemoryItem`：带范围、来源、保留期和敏感级别的长期记忆。
- `EvaluationDataset` / `EvalCase` / `EvalRun`：评测集、案例和结果。
- `AuditEvent`：安全相关操作的不可变审计记录。

### 4.2 关键状态

`Run.status`：

```text
queued -> running -> waiting_approval -> running
                   -> completed
                   -> failed
                   -> cancelled
```

`AgentVersion.status`：

```text
draft -> validating -> ready -> published -> deprecated
```

版本发布后不可原地修改；所有变更产生新版本，保证运行可复现和可回滚。

## 5. Module Design

### 5.1 Identity & Tenant

- 支持本地/OIDC 登录和服务账号；
- 每个请求必须携带租户上下文；
- PostgreSQL 查询默认带 `tenant_id`；
- 第一阶段使用 RBAC，后续对工具、知识库和环境增加 ABAC；
- 管理动作、密钥访问、发布、审批和工具执行写审计日志。

### 5.2 Model Gateway

统一接口应覆盖：

```python
class ModelProvider(Protocol):
    async def generate(self, request: ModelRequest) -> ModelResponse: ...
    async def stream(self, request: ModelRequest) -> AsyncIterator[ModelEvent]: ...
    async def embed(self, request: EmbeddingRequest) -> EmbeddingResponse: ...
```

职责包括：

- 模型别名与环境配置；
- 消息、工具、结构化输出和多模态字段标准化；
- 超时、重试、熔断、降级和幂等；
- 并发/Token 限流和租户配额；
- Prompt/Completion Token、价格快照和实际成本记账；
- 脱敏日志，不记录明文密钥。

重试只适用于可安全重试的错误。流式响应中途失败不得盲目重新执行有副作用的工具。

### 5.3 Agent Runtime

Runtime 负责：

1. 载入不可变的 AgentVersion；
2. 解析线程上下文和可用资源；
3. 执行 LangGraph 状态机；
4. 在每个节点前做权限、预算和取消检查；
5. 持久化 Checkpoint 与 RunStep；
6. 发出标准事件；
7. 等待审批后从 Checkpoint 恢复；
8. 写入最终输出、用量、Trace 与反馈入口。

Runtime 与控制面解耦。API 创建 `Run` 后，短任务可内联执行，长任务交给 Worker。生产环境应通过队列分发并使用幂等键避免重复执行。

### 5.4 Tool & MCP

支持三类工具：

- 内置函数：平台内部可信能力；
- HTTP Tool：OpenAPI/JSON Schema 描述的远程接口；
- MCP Tool：通过 MCP Server 动态发现与调用。

每个工具必须声明：

- 名称、描述、输入/输出 JSON Schema；
- 超时、重试、并发限制；
- `read_only`、`side_effect`、`destructive` 风险等级；
- 所需权限和允许的租户/环境；
- 是否需要人工审批；
- 允许访问的网络域和密钥引用。

工具执行器采用隔离适配器。未来代码执行类工具必须进入 Sandbox，限制 CPU、内存、时间、文件系统和网络；首期不提供任意代码执行。

### 5.5 Knowledge / RAG

摄取流水线：

```text
Upload -> Virus/Type Check -> Parse -> Normalize -> Chunk
       -> Metadata -> Embedding -> Index -> Ready
```

检索流水线：

```text
Query Rewrite -> Metadata Filter -> Hybrid Recall
              -> Rerank -> Context Pack -> Citation
```

关键要求：

- 原始文件和解析版本可追溯；
- Chunk 保存文档、页码/单元格、字符区间和权限标签；
- 向量检索和关键词检索可融合；
- 上下文装配受 Token 预算控制；
- 回答返回引用，引用能定位原文；
- 文档删除要同步删除索引和缓存；
- 检索严格继承源文档 ACL，不能跨权限召回。

首期文件类型建议：PDF、DOCX、TXT/Markdown；XLSX 在明确表格问答需求后加入。

### 5.6 Memory

- 短期记忆：Thread 消息和运行状态；
- 长期记忆：从对话中抽取、经策略允许后保存的用户/业务事实；
- 知识记忆：企业文档，由 Knowledge 模块负责。

长期记忆应包含来源、置信度、创建者、作用域、敏感级别、过期时间和删除状态。默认不自动永久保存敏感信息，用户可查看、纠正和删除。

### 5.7 Workflow & Human Approval

工作流节点至少包括：

- LLM；
- Tool；
- Retriever；
- Router/Condition；
- Transform；
- Human Approval；
- Start/End。

编辑器最终保存的是经过版本校验的声明式图，而不是任意前端 JSON。发布前检查无入口、死循环、缺失凭证、Schema 不兼容和超预算路径。

审批请求保存待执行动作的参数摘要、风险说明、过期时间和 Checkpoint。审批者不能修改原动作；修改参数应创建新的运行分支。

### 5.8 Evaluation

评测分三层：

1. 单元评测：Prompt、工具 Schema、检索器等模块；
2. 端到端离线评测：固定数据集上的任务成功率、引用正确性和成本；
3. 在线评测：用户反馈、采样审查、失败/超时/转人工率。

指标包括：

- Task Success / Exact Match / 规则评分；
- Tool Selection 与参数正确率；
- Retrieval Recall@K、MRR、引用忠实度；
- LLM Judge（必须校准，不能作为唯一发布门槛）；
- P50/P95 延迟、Token、成本、错误率；
- 安全策略违规率和人工审批率。

发布门禁使用“基线版本 vs 候选版本”对比，关键安全案例必须 100% 通过。

### 5.9 Observability

统一事件模型：

```text
run.created
run.started
step.started
model.delta
model.completed
tool.approval_required
tool.started
tool.completed
retrieval.completed
run.completed
run.failed
```

每条事件包含 `tenant_id`、`thread_id`、`run_id`、`step_id`、时间戳、序号和 Trace Context。模型输入、工具参数和检索文本按数据策略脱敏或只存摘要。

## 9. Code Style

Python 使用异步边界、类型标注和小型用例函数：

```python
async def create_run(command: CreateRun, actor: Actor) -> Run:
    await policy.require(actor, "run:create", command.agent_id)
    version = await versions.get_published(command.agent_id)
    return await runs.create(command=command, version=version)
```

TypeScript 开启 `strict`，组件只接收明确 Props，API 类型从 OpenAPI 生成：

```ts
type RunStatusProps = {
  status: "queued" | "running" | "completed" | "failed";
};
```

命名规则：

- Python 文件/函数使用 `snake_case`，类使用 `PascalCase`；
- Vue 组件使用 `PascalCase.vue`，组合函数使用 `useXxx.ts`；
- API 字段使用 `snake_case`，事件名使用 `domain.action`；
- 时间统一存 UTC ISO 8601，金额记录币种和价格快照。

## 10. Testing Strategy

- Domain/Application：纯单元测试，不依赖网络；
- API：FastAPI TestClient/HTTPX 集成测试；
- Infrastructure：通过 Testcontainers 或独立 Compose Profile 测试；
- Runtime：用确定性 Fake Model 与 Fake Tool 测试分支、重试、暂停和恢复；
- Web：Vitest + Vue Test Utils；关键发布流程用 Playwright；
- Contract：OpenAPI 快照和事件 Schema 兼容测试；
- Eval：固定数据集回归，结果作为发布门禁。

首期目标：核心领域与权限逻辑分支覆盖率不低于 80%，不是追求全仓机械覆盖率。

## 11. Security

- 密钥只保存加密引用，不写入源码、日志或前端；
- 租户隔离在 API、数据查询、向量检索、对象路径四层同时实施；
- 外部 URL 防 SSRF，使用域名白名单并阻止内网元数据地址；
- 上传文件限制类型、大小，进行恶意文件检测；
- Prompt Injection 视为不可信输入，检索文本不能改变系统权限；
- 工具调用前做服务端授权，不能依赖模型自觉；
- 有副作用动作记录幂等键、审批和审计；
- PII 支持脱敏、保留期、导出和删除。

## 12. Reliability and Performance

- API 无状态部署；运行状态通过数据库/Checkpoint 恢复；
- 模型和工具调用设置分层超时、最大重试和熔断；
- 每个 Run 设置最大步骤、Token、成本和执行时间；
- SSE 事件带递增序号，客户端断线后可从游标续传；
- Worker 使用租约与心跳识别僵尸任务；
- 指标初始目标：控制面 P95 < 300ms（不含模型），首 Token P95 可按模型分别设定；
- 生产前定义 PostgreSQL、对象存储和密钥的备份恢复演练。

## 13. Delivery Phases

### Phase 0：基础工程（当前）

- Monorepo、Web/API 健康入口、本地依赖、环境变量和技术规格。

### Phase 1：单 Agent 闭环

- 登录、Agent/Version、模型网关、Thread/Run、SSE、基本 Trace。

### Phase 2：知识与工具

- 文档摄取、混合检索、引用、HTTP Tool、MCP、权限和审批。

### Phase 3：评测与发布

- 数据集、离线评测、版本对比、发布门禁、成本看板。

### Phase 4：企业治理

- 多租户强化、配额、密钥托管、审计、SSO、Kubernetes 部署。

## 14. Boundaries

### Always

- 所有外部输入经过 Schema 校验；
- 所有资源访问带租户和权限检查；
- 发布使用不可变版本；
- 运行有预算、超时、取消与审计；
- 变更先更新本规格或对应 ADR，再写代码；
- 合并前执行相关测试和类型检查。

### Ask First

- 数据库破坏性迁移；
- 增加新的基础设施依赖；
- 改变认证方案、租户隔离模型或公开 API；
- 启用任意代码执行、开放互联网访问或自动执行高风险工具；
- 更换核心 Agent 框架。

### Never

- 提交真实密钥或用户敏感数据；
- 让模型绕过服务端权限；
- 在没有审计的情况下执行破坏性工具；
- 将 LLM Judge 作为唯一质量结论；
- 依赖不可恢复的内存状态执行长任务。

## 15. Success Criteria

- 本地依赖、Web 和 API 能按文档独立启动；
- 用户可完成“创建 Agent → 调试 → 查看 Trace → 评测 → 发布 → API 调用”闭环；
- Agent 运行失败或审批暂停后可从 Checkpoint 恢复；
- 每个输出能关联模型调用、工具、知识引用、版本和成本；
- 权限和租户隔离测试覆盖横向越权场景；
- 候选版本未通过安全回归时无法发布。

## 16. Open Questions

进入 Phase 1 前需要确认：

1. 首个业务场景是通用企业知识库，还是智能任务指挥 Agent？
2. 平台首期是单组织私有部署，还是直接做多租户 SaaS？
3. 首批必须支持哪些模型供应商？
4. 是否需要可视化拖拽工作流，还是先用表单/代码配置？
5. MCP Server 是平台托管，还是只连接外部 Server？
6. 是否存在涉密、等保、数据不出域或国产化要求？
7. 预期并发、单日 Run 数、文档规模和可接受成本是多少？

这些答案会影响身份体系、队列、存储、网络隔离和部署复杂度。在确认前，基础工程只保留扩展点，不提前实现重型基础设施。
