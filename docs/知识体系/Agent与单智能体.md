# Agent 与 Single-Agent（单智能体）系统学习指南

> 上位导航：[AI Agent 知识体系](README.md)

> 本文从定义、循环、规划、状态、规则筛选、可靠性到面试问题，系统说明如何设计一个可上线的单智能体。多智能体建立在这些基础之上，不能替代单智能体的工程治理。

## 0. Agent 到底是什么

Agent（智能体）可以定义为：由 LLM（大语言模型）根据目标和当前状态，在受控能力集合中动态决定下一步，通过工具观察和改变环境，直到满足终止条件的系统。

```text
Agent = Model + Instructions + Tools + Context + State + Runtime + Guardrails
```

只有“模型 + Prompt”通常只是一次生成调用；只有固定的 A→B→C 节点通常是 Workflow（工作流）。Agent 的关键特征是：路径不是完全预先写死，模型可以根据中间结果调整下一步。

## 1. Agent、Workflow 与普通聊天机器人

| 类型 | 路径 | 是否作用于外部环境 | 适合场景 |
|---|---|---|---|
| 聊天机器人 | 主要是问答 | 通常不产生副作用 | 咨询、解释、内容生成 |
| Workflow | 代码预定义 | 可以 | 稳定、可枚举、强一致流程 |
| Agent | 模型动态决策 | 通常通过工具 | 开放任务、路径依赖中间观察 |

Anthropic 将 Workflow 描述为通过预定义代码路径编排模型和工具，将 Agent 描述为由模型动态指导工具使用与执行过程。生产系统常把两者混合：外层用确定性工作流控制风险，局部开放节点交给 Agent 推理。

## 2. Agent Loop（智能体循环）

经典循环可以概括为 ReAct（推理与行动协同）：

```text
Goal（目标）
  → Observe（观察上下文与状态）
  → Think / Plan（推理 / 计划）
  → Act（调用工具或输出）
  → Observe（读取结果）
  → Update State（更新状态）
  → Continue / Replan / Stop（继续 / 重规划 / 终止）
```

真实实现不必暴露模型完整思维过程，但必须保存可审计的决策摘要、工具调用、结果和状态变化。

### 2.1 一个最小运行状态

```json
{
  "goal": "处理用户退款申请",
  "constraints": ["退款不超过已支付金额"],
  "plan": ["查询订单", "检查资格", "执行或请求审批"],
  "completed_steps": [],
  "pending_action": null,
  "attempt": 1,
  "budget": {"max_steps": 8, "deadline_ms": 15000},
  "status": "running"
}
```

State 应由运行时维护，不能只存在模型自然语言里。

## 3. 规划模式

### 3.1 Plan-and-Execute（先规划后执行）

先生成计划，再逐步执行。优点是目标清楚、易审查；缺点是计划可能在新信息出现后过时。因此要允许 Replanning（重规划），而不是盲目执行初始计划。

### 3.2 Incremental Planning（增量规划）

每次只决定下一步，适合高不确定环境。优点是灵活，缺点是容易短视、循环或丢失全局目标。

### 3.3 混合方式

保留高层里程碑，每一步基于 Observation 动态决定具体动作。多数长任务更适合这种方式。

### 3.4 Reflection / Critique（反思 / 批评）

让模型检查计划或结果可以发现遗漏，但不是免费的可靠性增强。它增加 Token、延迟，也可能把正确结果改错。只在失败代价高、存在明确检查标准或评测证明有效时使用。

## 4. Capability Routing（能力路由）

Agent 往往面对几十甚至上百种工具、知识库和子流程。全部暴露会降低选择准确率并扩大攻击面。

推荐路由链：

```text
请求
  → 硬规则过滤（权限、租户、环境、风险）
  → 意图与领域识别
  → 候选能力检索 / 分类
  → LLM 在候选集中选择
  → 执行前再次授权
```

常见实现：

- Rule-based Routing（规则路由）：确定、便宜、可审计；适合稳定强规则。
- Classifier Routing（分类器路由）：适合固定类别且样本充足。
- Semantic Routing（语义路由）：用 Embedding 匹配能力描述，适合大量工具初筛。
- LLM Routing（模型路由）：理解复杂意图，但需要约束候选集和回退机制。
- Hybrid Routing（混合路由）：生产中最常见。

## 5. 终止条件与进度判定

只设 `max_steps` 不够。完整终止机制应包括：

- Success Condition（成功条件）：基于环境状态或可验证输出，而非模型自称完成。
- Failure Condition（失败条件）：权限拒绝、不可恢复错误、依赖不可用。
- Budget Limit（预算限制）：步数、时间、Token、费用、工具次数。
- No-progress Detection（无进展检测）：状态没有新增、重复相同动作或错误。
- Human Escalation（人工升级）：高风险、长期不确定或需要业务裁决。
- Graceful Degradation（优雅降级）：返回已完成部分、缺失信息和可继续方式。

进度可以用结构化状态差异判断，例如新增有效证据、完成子目标、减少待办，而不是只让模型回答“是否有进展”。

## 6. 工具执行可靠性

### 6.1 Timeout（超时）

分别设置连接、读取、单工具、单步骤和整次 Run 的超时，避免某一层无限等待。

### 6.2 Retry（重试）

只重试短暂故障，例如网络抖动和限流；参数非法、权限拒绝等确定性错误不应重试。使用 Exponential Backoff（指数退避）和 Jitter（随机抖动），防止重试风暴。

### 6.3 Idempotency（幂等）

对付款、发消息、创建订单等副作用动作传入 Idempotency Key（幂等键）。同一逻辑动作即使因超时重放，也只生效一次。

### 6.4 Compensation（补偿）

跨系统操作通常没有全局事务。应为已完成步骤设计补偿动作，例如预订成功但付款失败时释放预订。补偿也可能失败，因此需要状态记录、重试与人工介入。

## 7. Checkpoint 与 Human-in-the-loop

在以下边界保存 Checkpoint：

- 工具副作用之前和之后；
- 等待人工审批之前；
- 长耗时任务阶段完成后；
- 外部依赖失败准备重试时；
- 上下文压缩前后。

Human-in-the-loop（人在回路）不只是弹一个确认框，而是：暂停运行、序列化状态、向审批者展示动作及风险、记录同意/拒绝/修改、恢复时重新验证环境是否变化。

## 8. State、Memory、Checkpoint 与 Trace

| 对象 | 用途 | 例子 |
|---|---|---|
| State | 当前任务的业务与控制状态 | 当前步骤、已查订单、剩余预算 |
| Memory | 跨任务值得复用的信息 | 用户偏好、过往解决经验 |
| Checkpoint | 可恢复的一致状态快照 | 暂停审批前的完整运行状态 |
| Trace | 解释实际执行过程 | 模型调用、工具耗时、路由决策 |

State 是“现在是什么”，Trace 是“怎样走到这里”，Checkpoint 是“从哪里继续”，Memory 是“以后什么值得再用”。

## 9. 常见失败与排错

### 9.1 一直循环调用工具

检查：工具结果是否明确表达成功/失败；状态是否更新；是否存在重复检测；终止条件是否可验证；模型是否看到了剩余预算。

### 9.2 工具选错

检查：候选是否太多；名称和描述是否重叠；参数 Schema 是否表达使用边界；是否缺少能力检索；是否存在错误示例。

### 9.3 模型说完成但实际没有

根因是把自然语言声明当作业务事实。应由代码读取数据库、文件、测试或工具结果，验证最终 Outcome（结果状态）。

### 9.4 部分成功后重试造成重复副作用

需要幂等键、执行记录和副作用前后 Checkpoint；恢复时先查询当前状态，再决定重放或补偿。

### 9.5 上下文越来越长

把稳定事实写入结构化 State；旧历史做摘要或检索；工具输出做裁剪；长任务使用持久化工作产物与上下文压缩。

## 10. 什么时候不要用 Agent

- 规则可以穷举且要求强确定性；
- 延迟预算极小；
- 每一步都需要严格审计且无法容忍概率决策；
- 没有可靠评测和安全执行边界；
- 任务只是简单查询、模板填充或单次分类；
- 引入 Agent 后没有可衡量的质量或效率收益。

此时使用普通代码、搜索、规则引擎或固定 Workflow 更合适。

## 11. 面试重点

### 11.1 什么是 Agent？和 Workflow 有什么区别？

答题要点：Agent 是模型依据目标和中间观察动态决定路径；Workflow 由代码预先定义路径。生产系统常混用：确定性骨架保证可靠，开放节点用 Agent 处理不确定性。

### 11.2 怎样防止 Agent 无限循环？

答题要点：最大步数只是最后保险；还要有成功/失败条件、时间与费用预算、重复动作检测、结构化进度、工具错误分类、重规划次数和人工升级。

### 11.3 单智能体怎样设计能力路由？

答题要点：先由权限和风险规则过滤；再按意图、领域或语义检索缩小候选；LLM 在候选中选择；执行前按真实参数再次授权。记录候选、选择理由和路由置信度。

### 11.4 Agent 如何保证工具副作用不重复？

答题要点：业务幂等键、执行状态表、副作用前后检查点、超时后先查状态再重试；跨系统失败用 Saga（长事务补偿）而不是假设全局事务。

### 11.5 怎样判断 Agent 真的完成任务？

答题要点：检查可验证的最终环境状态，例如数据库记录、测试结果、文件或外部 API 状态，而不是相信最终文本。开放质量再结合规则、模型评分器和人工校准。

### 11.6 为什么先做好单智能体再做多智能体？

答题要点：多智能体不会消除工具、状态、权限、终止和评测问题，反而把它们乘以多个节点，并增加通信、冲突和错误传播。先建立可测、可恢复的单体能力，才能判断拆分是否真有收益。

## 12. 术语速查

| 英文 | 中文 | 含义 |
|---|---|---|
| Agent Loop | 智能体循环 | 观察、决策、行动、再观察的迭代 |
| ReAct | 推理与行动协同 | 将推理和外部动作交错进行的方法 |
| Replanning | 重规划 | 根据新观察调整原计划 |
| Guardrail | 护栏 | 对输入、输出或工具执行施加限制 |
| Idempotency | 幂等 | 同一动作重复执行仍只产生一次效果 |
| Checkpoint | 检查点 | 可供暂停、失败后恢复的状态快照 |
| Outcome | 最终状态 | 任务对真实环境造成的可验证结果 |
| Human-in-the-loop | 人在回路 | 人参与审批、纠错或决策的机制 |
