# Security（安全）与 Governance（治理）系统学习指南

> 上位导航：[AI Agent 知识体系](README.md)

> Agent 安全的核心不是让模型“更听话”，而是限制系统在模型被诱导、误判或失控时仍然不能越过的边界。把 LLM 当不可信决策者，把工具调用当外部输入，把每个副作用当需要授权的真实操作。

## 0. Agent 扩大了什么风险

普通聊天模型主要产生文本；Agent 还会读取私有数据、调用工具、修改环境、长期记忆并委派其他 Agent，因此攻击面扩展到：

- Instructions（指令）与上下文；
- RAG 文档、网页、邮件、文件等不可信内容；
- Tool / MCP Server（工具 / MCP 服务器）；
- Memory（记忆）和共享状态；
- 身份令牌、密钥与租户数据；
- 多智能体消息和 Handoff（任务移交）；
- 代码执行、浏览器、文件系统和网络；
- Trace、日志、缓存与评测数据。

## 1. Threat Model（威胁模型）

设计前先回答：

1. 保护什么资产：数据、资金、账号、代码、基础设施还是声誉？
2. 攻击者是谁：匿名用户、租户用户、恶意文档、被攻陷工具或内部人员？
3. Agent 有哪些能力和凭证？
4. 数据从哪里进入、经过哪些模型和服务、流向哪里？
5. 最坏副作用和 Blast Radius（爆炸半径）是什么？
6. 哪些动作可逆，哪些必须在执行前阻止？

按照 NIST AI RMF（美国国家标准与技术研究院人工智能风险管理框架）的思路，应在治理、识别、衡量和管理整个生命周期持续处理风险，而不是上线前做一次安全检查。

## 2. Prompt Injection（提示词注入）

### 2.1 Direct Prompt Injection（直接提示词注入）

用户直接要求忽略系统规则、泄露信息或调用越权工具。

### 2.2 Indirect Prompt Injection（间接提示词注入）

恶意指令藏在网页、邮件、PDF、代码注释、工具返回或 RAG 文档中。Agent 读取内容后可能把数据当作指令。

### 2.3 为什么不能只靠 Prompt 防御

模型仍是概率系统，无法绝对区分自然语言中的“数据”和“命令”。有效防御是纵深的：

- 对外部内容建立不可信边界和来源标签；
- 在检索与上下文层隔离控制指令和数据；
- 按任务只暴露必要工具；
- 执行前由确定性策略重新授权；
- 高风险副作用要求人工审批；
- 限制网络、文件、密钥和数据访问；
- 检测异常工具链和数据外发。

## 3. Least Privilege（最小权限）

- 每个 Agent、工具和子任务只获得完成当前目标所需权限；
- 使用短期、范围受限且绑定受众的凭证；
- 读写工具分离，高风险写工具单独审批；
- 不把用户 ID、租户 ID 等模型参数当可信身份；
- 服务端从认证上下文取得主体，并做资源级授权；
- 多 Agent Handoff 时重新计算权限，不继承全部父权限；
- 任务结束或取消后立即撤销临时凭证。

## 4. Policy Engine 与 Guardrail

### 4.1 确定性策略层

负责身份、租户、资源、动作、额度、地域、时间、数据级别和审批规则。输出结构化决策并记录命中规则。

### 4.2 Guardrail（护栏）分层

- Input Guardrail（输入护栏）：检测不允许的请求、敏感数据和恶意输入。
- Output Guardrail（输出护栏）：检测数据泄露、不安全内容、格式和事实约束。
- Tool Guardrail（工具护栏）：每次调用前后校验工具、参数和结果。
- Runtime Guardrail（运行时护栏）：限制步骤、Token、费用、并发、网络和文件范围。

护栏失败应 Fail Closed（安全关闭）：校验器错误、参数无法解析或策略服务不可用时，高风险动作默认不执行。

## 5. Tool Security（工具安全）

执行前：

- Schema 与业务语义校验；
- 主体、租户、目标资源授权；
- 幂等键、金额、频率和风险检查；
- 必要的审批和二次确认；
- 参数中的 URL、路径、命令和查询安全检查。

执行中：

- Sandbox（沙箱）与进程隔离；
- 文件系统、网络域名、数据库和系统调用允许列表；
- CPU、内存、磁盘、时间和输出大小限制；
- 使用临时工作区和最小凭证。

执行后：

- 结构化结果与敏感字段过滤；
- 验证真实副作用；
- 记录调用主体、目的、参数摘要、结果与审批证据。

## 6. Data Exfiltration（数据外泄）

典型链路：Agent 从私有邮箱读取数据，再被恶意网页指令诱导，通过 HTTP、消息或日志工具发送出去。

治理：

- 对数据做 Classification（分级）和 Taint Tracking（污点追踪）；
- 限制高敏数据可流向的模型、工具和域名；
- 将“读取私有数据”和“外部写入”视为危险能力组合；
- 对外发内容做 DLP（数据防泄漏）检查；
- 使用 Egress Control（出站控制）和域名允许列表；
- Trace 和错误信息不记录密钥与完整敏感内容。

## 7. Memory 与 RAG 安全

### 7.1 Memory Poisoning（记忆投毒）

攻击者诱导系统写入错误偏好、永久指令或恶意经验。应限制可写类型，区分来源与置信度，用户确认关键记忆，并支持版本、回滚和删除。

### 7.2 RAG Poisoning（检索投毒）

恶意或低质量文档进入索引，影响检索和生成。应验证来源、控制写权限、做内容扫描、版本发布、引用核验和快速下架。

### 7.3 Tenant Isolation（租户隔离）

租户过滤必须进入存储查询与检索层。缓存键、Embedding 索引、Trace、评测样本和备份也要隔离，不能只在最终答案前过滤。

## 8. Multi-Agent Security（多智能体安全）

- 子 Agent 只接收必要上下文和能力；
- Agent 间消息不能自动升级为高优先级指令；
- 限制委派深度、数量和可调用角色；
- 对共享状态做写权限和版本控制；
- 中央策略层仲裁高风险副作用；
- 被攻陷或异常 Agent 可单独吊销权限和隔离；
- 聚合器检查来源、冲突和敏感数据，而不是直接拼接。

## 9. Human Approval（人工审批）

适合：不可逆、金额高、对外发布、权限提升、删除、隐私访问和不确定风险操作。

审批界面应展示：

- 具体动作和最终参数；
- 目标资源、影响范围和可逆性；
- Agent 使用的依据与风险提示；
- 谁请求、谁审批、何时过期；
- 批准、拒绝或修改后的行为。

Approval Fatigue（审批疲劳）会让人机械点击通过。应通过风险分级减少无价值审批，而不是对每个低风险读操作都弹窗。

## 10. Secrets（密钥）治理

- 密钥保存在 Secret Manager（密钥管理器），不进入 Prompt、Memory 或代码库；
- 工具在执行侧注入凭证，模型只看到能力，不看到密钥；
- 使用短期令牌、最小 Scope 和自动轮换；
- 日志、异常、Trace 和工具结果默认脱敏；
- 防止 Server-Side Request Forgery（服务端请求伪造）访问云元数据或内部服务；
- 泄露后可快速吊销、审计和确定影响范围。

## 11. Audit（审计）与治理

审计记录至少包括：

- 用户、服务身份、租户与会话；
- Agent、模型、Prompt、策略、工具和知识版本；
- 权限决策和命中规则；
- 工具动作、参数摘要、幂等键和真实结果；
- 审批请求与审批者；
- 数据来源和流向；
- 异常、拒绝、恢复和人工介入。

同时落实：访问控制、加密、保留期限、用户删除请求、跨境与供应商治理、Incident Response（事件响应）和定期 Red Teaming（红队测试）。

## 12. 安全测试

- 直接与间接 Prompt Injection；
- 越权读取和跨租户检索；
- 工具参数篡改、路径穿越、命令注入与 SSRF；
- 记忆投毒和 RAG 投毒；
- 多 Agent 冒充、权限继承和递归委派；
- 审批绕过、超时恢复后旧授权复用；
- 敏感数据经答案、日志、URL 或工具外发；
- 资源耗尽、无限循环和成本攻击；
- 被攻陷 MCP Server 返回恶意结果。

安全用例必须进入自动回归，严重违规使用零容忍断言，而非与普通质量分加权平均后被掩盖。

## 13. 常见失败与排错

| 现象 | 常见根因 | 治理 |
|---|---|---|
| Prompt 要求禁止但仍越权 | 把 Prompt 当权限系统 | 服务端授权、最小权限、执行前策略 |
| RAG 文档诱导调用工具 | 未区分数据与指令 | 信任分区、工具收缩、调用护栏 |
| 审批后参数被替换 | 审批未绑定具体参数 | 对动作参数做哈希并绑定审批 |
| 子 Agent 访问过多数据 | 继承父 Agent 权限和历史 | Handoff 重新授权、最小上下文 |
| Trace 泄露敏感信息 | 默认记录完整输入输出 | 字段级脱敏、采样、访问和保留策略 |
| 恢复任务使用过期授权 | 信任旧 Checkpoint | 恢复时重新验证身份和权限 |

## 14. 面试重点

### 14.1 如何防御 Prompt Injection？

答题要点：承认不能只靠 Prompt 绝对解决；将外部内容视为不可信数据，隔离指令层；缩小工具和数据权限；执行前确定性授权；高风险审批；沙箱、出站控制、监控和对抗评测。

### 14.2 Guardrail 应放在哪里？

答题要点：输入、输出、每次工具调用和运行时都有独立护栏。最重要的是副作用执行边界；参数解析失败或策略不可用时高风险动作安全关闭。

### 14.3 多租户 RAG 怎样防止数据串读？

答题要点：在检索前按租户分区或过滤，文档、索引、缓存、Trace 和备份都携带租户边界；服务端从认证上下文获取租户，不能信模型参数。

### 14.4 人工审批怎样设计才安全？

答题要点：审批具体动作、参数、目标和时效；保存身份和证据；恢复时检查环境变化；参数改变重新审批；按风险分级避免审批疲劳。

### 14.5 MCP Server 连接成功是否代表可信？

答题要点：不是。Host 要审查 Server 来源和能力，每次调用做授权，使用正确受众和最小 Scope 的令牌，禁止透传；本地 Server 也可能访问主机资源。

## 15. 术语速查

| 英文 | 中文 | 含义 |
|---|---|---|
| Threat Model | 威胁模型 | 分析资产、攻击者、路径和影响 |
| Prompt Injection | 提示词注入 | 诱导模型违背可信指令或误用能力 |
| Least Privilege | 最小权限 | 只授予当前任务必要能力 |
| Data Exfiltration | 数据外泄 | 敏感数据被发送到未授权位置 |
| Sandbox | 沙箱 | 限制代码或工具影响范围的隔离环境 |
| Fail Closed | 安全关闭 | 安全组件失败时默认拒绝高风险操作 |
| DLP | 数据防泄漏 | 检测和阻止敏感数据不当流出 |
| Blast Radius | 爆炸半径 | 故障或攻击可影响的最大范围 |
| Red Teaming | 红队测试 | 用对抗方式发现系统弱点 |
