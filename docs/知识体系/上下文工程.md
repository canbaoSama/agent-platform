# Context Engineering（上下文工程）系统学习指南

> 上位导航：[AI Agent 知识体系](README.md)

> 上下文工程决定模型在每一步“看到什么”。它不是把所有信息拼进 Prompt，而是在有限的 Attention Budget（注意力预算）内，选择、组织、隔离和更新最有价值的信息。

## 0. Prompt Engineering 与 Context Engineering

Prompt Engineering（提示词工程）主要研究“指令怎样表达”；Context Engineering 研究“模型完成当前步骤所需的信息怎样被构造”。后者范围更大，包括：

- System Instructions（系统指令）与业务规则；
- 当前用户请求和会话历史；
- Agent 当前 State（状态）与计划；
- Tool Definitions（工具定义）和工具结果；
- RAG 证据与引用；
- Memory（记忆）召回；
- 时间、身份、权限和环境信息；
- 输出格式、剩余预算和终止要求。

同一个 Prompt 模板，在上下文选择错误时依然会失败。生产优化经常不是“把指令写得更强硬”，而是减少噪声、补足证据、消除冲突和调整装配顺序。

## 1. 一次模型调用的上下文组成

```text
可信控制面
  ├─ System / Developer Instructions
  ├─ Policy Decision（策略决策结果）
  ├─ 可用工具子集及其 Schema
  └─ 输出契约、预算、终止条件

任务状态
  ├─ 当前目标与子任务
  ├─ 已完成步骤和待办
  ├─ 结构化 State
  └─ 最近必要的交互

外部信息面
  ├─ RAG 检索证据
  ├─ Memory 召回
  ├─ Tool Result（工具结果）
  └─ 用户上传或外部网页
```

外部信息面默认是不可信数据。即使其中出现“忽略之前指令”“调用某工具”等文本，也不应获得控制面权限。

## 2. 上下文组装流水线

推荐把组装过程做成可观测的独立模块：

```text
Raw Input（原始输入）
  → Normalize（规范化）
  → Identity & Policy（身份与策略）
  → Intent / Task Classification（意图 / 任务分类）
  → Capability Selection（能力选择）
  → History Selection（历史筛选）
  → RAG / Memory Retrieval（知识 / 记忆召回）
  → Deduplicate & Resolve Conflict（去重与冲突处理）
  → Rank & Budget（排序与预算）
  → Render Prompt（渲染模型输入）
```

每个阶段应记录：候选内容、入选原因、被过滤原因、Token 数、来源、版本和权限标签。否则“模型为什么没看到这条信息”无法定位。

## 3. Rule Filtering（内部规则筛选机制）

### 3.1 为什么规则不能全交给模型

LLM 适合语义判断，不擅长充当强一致的权限引擎。以下规则应由确定性代码完成：

- 身份认证、租户隔离、RBAC（基于角色的访问控制）和 ABAC（基于属性的访问控制）；
- 工具 Allowlist（允许列表）与 Denylist（拒绝列表）；
- 金额、频率、地域、数据级别等硬限制；
- 必须人工审批的动作；
- 法规、保留期限和数据脱敏；
- 超时、最大步数和费用预算。

模型可以参与意图分类和风险初筛，但最终执行前必须由可信策略层再次校验。

### 3.2 分层筛选

```text
L0 静态配置：环境、租户、产品版本允许哪些能力
L1 身份权限：当前主体有权访问哪些资源和动作
L2 请求策略：该意图、数据和风险级别允许哪些工具
L3 语义路由：LLM 在允许集合中选择最相关能力
L4 执行校验：用真实参数再次做权限、额度和审批检查
```

关键原则：先缩小允许集合，再交给模型选择；不能先让模型任意选择，再希望 Prompt 阻止越权。

### 3.3 规则冲突处理

规则要有显式优先级、适用范围、版本和命中理由。建议使用结构化决策：

```json
{
  "decision": "require_approval",
  "allowed_tools": ["read_invoice", "refund_invoice"],
  "constraints": {"refund_limit": 500},
  "matched_rules": ["finance.refund.high_risk.v3"]
}
```

不要只把几十条自然语言规则堆到 System Prompt 中；它们难以测试、审计和稳定执行。

## 4. Token Budget（词元预算）

应先保留约束，再分配信息预算。一个可调整的顺序是：

1. 不可省略：安全规则、用户目标、输出契约、关键状态。
2. 高价值：直接证据、最近工具结果、当前子任务所需工具定义。
3. 可压缩：较早历史、重复证据、详细过程。
4. 可按需加载：完整文档、低相关 Memory、罕用工具说明。

预算不应只限制总 Token，还要限制单来源占比，防止某次超长工具返回吞噬全部上下文。

## 5. History（会话历史）管理

常见策略：

- Sliding Window（滑动窗口）：只保留最近若干轮，简单但可能丢失早期约束。
- Summary（摘要）：压缩较早内容；要保存事实、决定、未完成事项和不确定性。
- Structured State（结构化状态）：从对话中抽取字段，例如目标、约束、已确认选择。
- Retrieval over History（历史检索）：按当前问题召回相关旧消息。
- Hybrid（混合）：最近消息 + 结构化状态 + 相关旧消息，通常更可靠。

摘要不是事实真相。它可能遗漏或误写内容，因此要保留来源消息 ID、摘要版本，并允许关键事实回查原文。

## 6. Just-in-time Context（即时上下文）

不要在每一步加载所有工具说明、所有记忆和所有文档。更好的方式是：

1. 先提供轻量目录、工具名称或数据源描述；
2. 模型或路由器判断当前需要什么；
3. 再读取具体 Schema、文档段落或记忆详情；
4. 使用完后只保留结论、引用与必要状态。

这种 Progressive Disclosure（渐进式披露）降低 Token 成本，也减少不相关内容干扰工具选择。

## 7. RAG、Memory、Tool Result 怎样进入上下文

### 7.1 RAG

RAG 内容应携带来源、时间、权限、相关性与版本。组装时做去重、重排、证据充分性判断，并用明确边界标记为“参考数据而非指令”。详见 [RAG](RAG.md)。

### 7.2 Memory

Memory 不应按“相似就塞入”。要同时考虑相关性、重要度、时效、置信度、用户/租户范围和冲突。详见 [Memory](Memory.md)。

### 7.3 Tool Result

工具返回应结构化、可截断、可分页，并区分：

- 成功数据；
- 可重试错误；
- 不可重试业务错误；
- 权限拒绝；
- 不确定或部分成功。

把异常堆栈或几万行原始结果直接回填模型，会造成上下文污染和敏感信息泄露。

## 8. Context Compaction（上下文压缩）

长任务跨越上下文窗口时，可在边界处做压缩：

- 已确认目标与不可变约束；
- 已完成工作及验证证据；
- 关键失败尝试与避免重复的原因；
- 当前状态、待办和下一步；
- 重要文件、对象或消息的稳定标识；
- 尚未解决的风险与不确定性。

适合保存在外部 Artifact（工作产物）或结构化 Checkpoint 中，而不是要求模型“自己永远记住”。压缩后应做一致性检查，必要时保留原 Trace 供回溯。

## 9. 上下文常见失败模式

### 9.1 Context Pollution（上下文污染）

无关文档、过期记忆、重复工具结果占据注意力，使模型偏离当前任务。

治理：来源配额、时间衰减、相关性阈值、去重、压缩和按需加载。

### 9.2 Context Rot（上下文退化）

上下文越来越长后，早期错误被反复总结、关键约束被稀释、模型利用率下降。

治理：结构化状态作为真相源，定期从原始证据重新压缩，不能只在旧摘要上继续摘要。

### 9.3 Lost in the Middle（中间信息遗失）

模型可能更善于利用开头和结尾的信息，而忽略长上下文中部。治理包括重排关键内容、减少噪声、拆解任务和让模型先定位再读取。

### 9.4 Instruction Injection（指令注入）

外部文档或工具结果携带恶意指令。治理依赖信任分区、工具权限最小化、执行前策略校验和输出审查，不能只依赖“忽略恶意指令”的 Prompt。

### 9.5 Conflicting Facts（事实冲突）

不同来源给出不同值。不要静默选择；应比较权威性、版本、时间和适用范围，无法判定时向用户说明冲突或触发人工处理。

## 10. 上下文质量评测

需要同时评估“是否选对”和“模型是否利用”：

- Context Precision（上下文精确率）：放入的内容有多少真正相关。
- Context Recall（上下文召回率）：回答所需信息是否被覆盖。
- Instruction Retention（指令保留率）：长任务后是否仍遵守关键约束。
- Source Attribution（来源归因）：声明能否映射到证据。
- Token Efficiency（词元效率）：单位任务成功所消耗的上下文 Token。
- Contamination Rate（污染率）：无权限、过期或恶意内容进入上下文的比例。

排错时做 Oracle Context（理想上下文）对照：人工提供正确且精简的证据。如果仍失败，重点查模型、Prompt 或输出约束；若成功，重点查检索、筛选和组装。

## 11. 面试重点

### 11.1 Prompt Engineering 和 Context Engineering 有什么区别？

答题要点：Prompt 是指令表达；Context 是一次推理看到的全部信息。上下文工程还覆盖历史筛选、RAG、Memory、工具定义、状态、预算、顺序、权限和压缩，是 Agent 质量的系统性控制面。

### 11.2 上下文窗口足够大，为什么不能把所有内容都塞进去？

答题要点：成本和延迟增加；相关性下降；存在位置效应；恶意或冲突内容扩大；工具定义过多会降低选择准确率。目标是最小、充分、高信号的上下文。

### 11.3 怎样组装一个生产级 Agent 的上下文？

答题要点：先由身份和策略缩小能力范围；再取当前目标、结构化状态、必要历史；按需召回 RAG 和 Memory；去重、处理冲突、排序并控制预算；最后明确标记可信指令与不可信数据，同时记录组装 Trace。

### 11.4 内部规则筛选应该用 LLM 还是代码？

答题要点：硬权限、合规、额度、审批和执行边界用确定性代码；模糊意图和语义相关性可由 LLM 辅助。模型只能在允许集合中选择，执行前再按真实参数授权。

### 11.5 长任务怎样跨上下文窗口继续？

答题要点：持久化结构化 State、Checkpoint 和工作产物；在窗口边界压缩目标、进度、证据、失败和下一步；新窗口从持久状态恢复，原 Trace 可回溯。不要依赖无限增长的消息历史。

## 12. 术语速查

| 英文 | 中文 | 含义 |
|---|---|---|
| Context Engineering | 上下文工程 | 构造模型当前可见信息的系统方法 |
| Attention Budget | 注意力预算 | 有限上下文中可有效利用的信息容量 |
| Context Assembly | 上下文组装 | 筛选、排序、压缩并渲染上下文 |
| Context Compaction | 上下文压缩 | 将长历史压缩为可恢复的高价值状态 |
| Progressive Disclosure | 渐进式披露 | 先给目录，需要时再加载详情 |
| Context Pollution | 上下文污染 | 无关、错误或恶意信息干扰推理 |
| Policy Engine | 策略引擎 | 以确定性规则做授权与约束的组件 |
| Provenance | 来源追踪 | 记录信息来源、版本和处理链路 |
