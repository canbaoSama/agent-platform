# RAG（检索增强生成）系统学习指南

> 目标：从原理、组件、排错、评测到生产落地，系统掌握 RAG（Retrieval-Augmented Generation，检索增强生成）。本文强调“为什么这样设计”，而不只是罗列框架和模型名称。

> 上位导航：[AI Agent 知识体系](README.md)。RAG 负责为当前问题提供外部证据；它与 [Memory（记忆）](Memory.md)、[Context Engineering（上下文工程）](上下文工程.md) 和 [Tool（工具）](Tool与MCP.md) 关系紧密，但写入来源、生命周期和治理目标不同。

建议按以下顺序学习：

| 阶段 | 章节 | 学习目标 |
| --- | --- | --- |
| 建立概念 | 0～1 | 理解 RAG 解决什么问题以及完整数据流 |
| 掌握基础组件 | 2～8 | 学会解析、分块、向量索引、查询、检索、重排和生成 |
| 学会诊断质量 | 9～11 | 能定位错误并理解幻觉治理与检测 |
| 学习进阶架构 | 12～14 | 理解 CRAG、Self-RAG、RAPTOR、GraphRAG 和 Agentic RAG |
| 掌握生产能力 | 15～19 | 完成权限、评测、运维、多模态与方案选型 |
| 复习术语 | 20 | 建立中英文概念映射 |

## 0. 先建立全局认识

### 0.1 RAG 到底解决什么问题

LLM（Large Language Model，大语言模型）的知识主要来自训练参数，因此存在三个天然限制：

1. **知识会过期**：训练结束后的新信息不会自动进入模型参数；
2. **不知道企业私有数据**：内部制度、项目文档和业务数据库不在公开训练数据中；
3. **答案难以追溯**：即使模型回答正确，也不一定能指出可靠来源。

RAG 的基本思想是：回答前先从外部知识源中找到证据，再把证据放入模型上下文中生成答案。原始 RAG 论文把语言模型的 Parametric Memory（参数化记忆）和外部的 Non-parametric Memory（非参数化记忆）结合起来，以便更新知识并提供来源依据。[原始 RAG 论文](https://arxiv.org/abs/2005.11401)

```text
用户问题
  -> 检索证据
  -> 把证据装入上下文
  -> 模型基于证据生成
  -> 校验答案与引用
```

RAG 能降低无依据回答的概率，但不能自动消除幻觉。检索到错误资料、漏掉关键资料或模型不忠于资料时，答案仍会出错。

### 0.2 RAG、长上下文和微调的关系

| 技术 | 主要解决的问题 | 不擅长的问题 |
| --- | --- | --- |
| RAG（检索增强生成） | 动态知识、私有知识、引用与可追溯性 | 风格固化、稳定行为训练 |
| Long Context（长上下文） | 一次处理少量长文档、跨段阅读 | 大规模知识库检索、持续更新、权限过滤 |
| Fine-tuning（微调） | 风格、格式、领域任务行为和稳定模式 | 频繁变化的事实知识、精确引用 |

三者不是互斥关系。常见组合是：微调负责“怎么回答”，RAG 负责“依据什么回答”，长上下文负责“本次需要阅读多少材料”。

### 0.3 RAG 的技术演进

- **Naive RAG（朴素 RAG）**：一次检索，直接把 Top K 结果交给模型；
- **Advanced RAG（高级 RAG）**：增加查询改写、混合检索、重排序、上下文压缩和答案校验；
- **Modular RAG（模块化 RAG）**：解析、检索、排序、生成和校验组件可独立替换；
- **GraphRAG（图增强 RAG）**：使用实体关系图和社区摘要解决关系与全局问题；
- **Agentic RAG（智能体式 RAG）**：由 Agent（智能体）动态决定检索工具、轮次和停止条件。

系统学习时应先掌握 Advanced RAG，再按问题类型学习 GraphRAG 和 Agentic RAG。复杂架构不是基础检索质量差的补救措施。

### 0.4 一条问题如何经过完整链路

假设用户问：“设备出现 `Error_0x884` 应该怎么处理？”

1. 服务端识别用户身份和可访问的设备文档；
2. Query Understanding（查询理解）提取精确错误码和设备型号；
3. BM25（关键词相关性算法）准确匹配错误码；
4. Dense Retrieval（密集语义检索）召回描述相同故障但用词不同的文档；
5. RRF（倒数排名融合）合并两路候选；
6. Reranker（重排序模型）把真正包含解决步骤的文档排在前面；
7. Parent Retrieval（父块检索）补齐该步骤所在的完整章节；
8. Context Packing（上下文组装）在 Token（词元）预算内去重，并保留标题、版本和页码；
9. 模型只根据证据生成步骤和引用；
10. Claim Verification（声明核验）检查每个关键步骤是否有原文支持。

这个例子说明：RAG 的质量来自整条链路，而不是只来自向量模型。

## 1. 端到端架构

### 1.1 离线索引链路

```text
数据源
  -> 解析与版面识别
  -> 清洗、去重和版本治理
  -> Chunking（分块）
  -> Metadata（元数据）与 ACL（访问控制列表）
  -> Embedding（向量化）
  -> 建立关键词、向量或图索引
  -> 质量校验
  -> 发布索引版本
```

离线链路负责把原始资料变成“可检索、可过滤、可引用、可更新”的知识单元。

### 1.2 在线检索生成链路

```text
用户问题
  -> 身份认证与权限解析
  -> 查询分类、改写或分解
  -> 权限与 Metadata 前置过滤
  -> 多路候选召回
  -> 去重与结果融合
  -> Rerank（重排序）
  -> 上下文扩展与组装
  -> Evidence Sufficiency（证据充分性）判断
  -> LLM 生成
  -> 引用与事实校验
  -> 返回答案、澄清或拒答
```

### 1.3 反馈闭环

```text
Trace（链路追踪）
  + 离线评测
  + 线上抽样
  + 用户反馈
  + 人工复核
        ↓
Bad Case（失败案例）分类
        ↓
更新评测集和系统策略
```

RAG 是持续运营的检索系统，不是部署一次就结束的模型功能。

## 2. 文档解析与数据治理

### 2.1 为什么解析决定质量上限

如果 PDF 的阅读顺序错了、表头丢了、标题和正文关系被破坏，后面的 Embedding 和 Reranker 只能在错误数据上工作。因此排查 RAG 时，第一步不是换向量模型，而是确认知识是否被正确解析。

### 2.2 不同文档的解析重点

| 数据类型 | 必须保留的结构 | 常见问题 |
| --- | --- | --- |
| Markdown / HTML | 标题层级、段落、列表、代码块、链接 | 导航和正文混在一起 |
| PDF | 阅读顺序、页码、版面、表格、图片说明 | 双栏错序、跨页表格、扫描页无文本 |
| Word | 标题样式、正文、表格、批注和版本 | 只读取纯文本导致层级丢失 |
| PPT | 页标题、文本框、图表和备注 | 元素顺序与视觉顺序不一致 |
| Excel / CSV | 表头、字段、单位、工作表和行列关系 | 单元格脱离表头后失去含义 |
| 代码仓库 | 文件路径、模块、类、函数、符号和调用关系 | 按字符切断函数或类 |
| 数据库 | Schema（模式）、字段说明、主外键和数据权限 | 把结构化计算强行转成文本检索 |

### 2.3 清洗原则

- 删除页眉、页脚、导航、广告和重复模板；
- 保留错误码、单位、条款号、产品型号等业务关键字符串；
- 统一编码、空白、标点和基础格式；
- 不要为了“文本干净”而改写原始事实；
- 对 OCR（Optical Character Recognition，光学字符识别）结果保存置信度和原图定位；
- 表格和公式解析失败时，应标记失败而不是静默丢弃。

### 2.4 去重、冲突与版本

每份文档需要保存来源、版本、生效时间、失效时间和更新时间。重复或冲突内容应有明确策略：

- 完全重复：使用 Content Hash（内容哈希）去重；
- 同一文档不同版本：优先有效版本，同时保留历史审计；
- 不同权威来源冲突：保留来源和权威等级，在答案中暴露冲突；
- 删除或撤权：同步清理索引、缓存和派生数据。

“最新”不一定等于“当前有效”。法规、合同和制度应以生效状态为准。

## 3. Chunking（分块）

### 3.1 为什么要分块

整篇文档直接做一个向量，会把多个主题压进同一表示，难以精确召回；切得太碎，又会破坏完整证据。分块要平衡：

1. **语义完整性**：单块能否独立表达一个事实或步骤；
2. **检索粒度**：是否容易找到所需位置；
3. **上下文成本**：进入重排序和模型的 Token 是否可控。

### 3.2 常见分块策略

| 策略 | 做法 | 优点 | 局限 | 适用场景 |
| --- | --- | --- | --- | --- |
| Fixed-size Chunking（固定长度分块） | 按字符或 Token 截断 | 简单、快速、适合基线 | 容易切断标题、句子和表格 | 日志、快速原型 |
| Recursive Chunking（递归分块） | 依次尝试章节、段落、句子等边界 | 效果与成本较平衡 | 依赖分隔符质量 | 通用文档 |
| Sentence Chunking（句子分块） | 先分句，再聚合到目标大小 | 不切断单句 | 远距离上下文仍可能丢失 | FAQ、对话和短段落 |
| Structure-aware Chunking（结构感知分块） | 按标题、条款、表格、函数等结构切分 | 可解释、语义稳定 | 依赖解析质量 | 手册、合同、代码和网页 |
| Semantic Chunking（语义分块） | 在语义变化明显的位置切分 | 适合无明显结构长文 | 成本高且依赖模型 | 论文、访谈和混合文本 |
| LLM-based Chunking（大模型分块） | 让模型判断主题与知识单元 | 能理解复杂逻辑 | 成本、延迟和稳定性较差 | 高价值离线文档 |

生产系统通常采用混合策略：先按文档结构粗切，再对超长章节递归或语义细分，代码和表格等原子结构保持完整。

### 3.3 Chunk Size（块大小）怎么选

不存在通用最佳值。下面只能作为首轮实验范围，而不是行业标准：

| 文档类型 | 可作为起点的粒度 | 更重要的边界 |
| --- | --- | --- |
| FAQ | 一个问题加一个完整答案 | 问答对不能分开 |
| 制度和技术手册 | 一个小节或若干完整段落 | 标题、步骤和注意事项 |
| 合同和法规 | 一个完整条款及必要上位标题 | 条款号、定义和引用关系 |
| 代码 | 一个函数、类或逻辑块 | 语法和符号边界 |
| 表格 | 一张小表或带表头的若干行 | 表名、表头、单位和主键 |
| 叙事长文 | 若干语义连续段落 | 主题变化位置 |

参数选择方法：

1. 先按结构得到自然块；
2. 只对超出模型或索引限制的块继续切分；
3. 建立包含短事实、多跳、表格和跨段问题的评测集；
4. 比较 Recall@K（前 K 项召回率）、答案质量、延迟与成本；
5. 按文档类型保存不同配置，不要全库共用一个值。

### 3.4 Overlap（重叠区间）

Overlap 在相邻块之间重复一小段内容，用来缓解边界信息丢失。它的代价是索引膨胀、重复召回和上下文浪费。

实践中可把块大小的 10%～20% 作为首轮实验值，但应通过评测调整。结构感知分块已经保持完整语义时，不一定需要大量重叠。

### 3.5 Parent-Child Retrieval（父子块检索）

父子块又叫 Small-to-Big Retrieval（小块召回、大块生成）：

```text
父章节 800～1500 Tokens
  ├─ 子块 A 200～400 Tokens
  ├─ 子块 B 200～400 Tokens
  └─ 子块 C 200～400 Tokens
```

- 子块用于检索，定位更精确；
- 命中后取父块或相邻块给模型，证据更完整；
- 父块需要有 Token 上限，不能命中一个句子就返回整本手册。

### 3.6 标题与正文分离：语义断裂

固定长度分块可能把标题放在上一个 Chunk 末尾，把对应正文放进下一个 Chunk。查询命中标题后，返回的正文却属于上一节。

定位方法：

1. 将召回块映射回原文并高亮切分边界；
2. 检查边界是否落在标题后、列表中或表格内部；
3. 构造“标题 + 正文核心词”测试集；
4. 统计正确正文是否进入 Top K；
5. 分析高分但答非所问的线上案例。

解决顺序：

1. 恢复标题层级并做结构感知分块；
2. 保存 `title_path`（标题路径）、`section_id`（章节标识）和 `parent_id`（父块标识）；
3. 将父标题作为检索字段或文本前缀；
4. 命中子块后扩展父块或相邻块；
5. 用 Overlap 临时缓解；
6. 用 Reranker 降低“标题相关但正文不支持”的结果。

只调 Chunk Size 不能根治结构丢失。

## 4. Metadata（元数据）

### 4.1 元数据为什么重要

元数据同时服务于检索过滤、权限、引用、版本治理和排错。正文告诉系统“内容是什么”，元数据告诉系统“它来自哪里、何时有效、谁能看”。

### 4.2 推荐字段

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `document_id` | 源文档唯一标识 | 更新、删除和追踪 |
| `chunk_id` | 分块唯一标识 | 结果定位和引用 |
| `parent_id` | 父块标识 | 父子块扩展 |
| `title_path` | 完整标题路径 | 语义补充和导航 |
| `page_number` | 页码或位置 | 可点击引用 |
| `chunk_type` | 文本、表格、代码或图片 | 检索路由 |
| `source_uri` | 原始来源 | 溯源 |
| `version` | 文档版本 | 冲突处理 |
| `effective_at` | 生效时间 | 时效过滤 |
| `updated_at` | 更新时间 | 新鲜度排序 |
| `tenant_id` | 租户标识 | 多租户隔离 |
| `acl` | 访问控制列表 | 权限过滤 |
| `content_hash` | 内容哈希 | 增量更新和去重 |

### 4.3 元数据的两个常见误区

- 字段写进数据库但没有建立过滤索引，查询时性能很差；
- 让模型自己生成权限过滤条件，导致用户可通过提示词影响安全边界。

权限条件必须由服务端根据已认证身份生成。

## 5. Embedding（向量化）与向量索引

### 5.1 Embedding 在做什么

Embedding Model（嵌入模型）把 Query（查询）和文档映射为向量。语义接近的内容在向量空间中距离更近，从而可以用相似度查找。

常见相似度：

- Cosine Similarity（余弦相似度）：比较方向；
- Dot Product（点积）：比较向量内积；
- Euclidean Distance（欧氏距离）：比较空间距离。

必须按照模型说明使用匹配的归一化方式和距离函数。更高维度并不自动意味着更好的业务召回。

### 5.2 Bi-Encoder（双塔编码器）

Query 和文档分别编码，文档向量可提前离线计算，因此检索速度快。大多数密集检索器属于这种结构。缺点是 Query 与文档在编码阶段没有逐 Token 交互，只能做粗粒度相关性判断。

### 5.3 Embedding 模型如何选

不要只看公开榜单，应从以下维度评测：

- 中文、英文和多语言能力；
- 是否适配查询到文档的非对称检索；
- 最大输入长度和长文本截断方式；
- 对专业术语、代码和表格的能力；
- 向量维度、存储成本和推理吞吐；
- 是否需要特定 Query Prefix（查询前缀）或 Instruction（任务指令）；
- 是否允许私有部署以及数据合规要求。

至少使用本领域标注数据评估 Recall@K 和 MRR（平均倒数排名），再决定模型。中文知识库、代码库和多语言知识库可能需要不同模型或不同索引。

### 5.4 ANN（近似最近邻）索引

向量数量较少时可以做 Flat Search（全量精确搜索）；数据量增大后通常使用 ANN，以少量召回损失换取查询速度。

| 索引 | 中文解释 | 优点 | 代价 | 适用情况 |
| --- | --- | --- | --- | --- |
| Flat | 全量精确搜索 | 结果精确、适合建立基线 | 数据大时慢 | 小数据集、评测 Ground Truth（真实基准） |
| HNSW | 层次可导航小世界图 | 查询快、召回高、无需训练 | 内存占用较高 | 中大型内存型检索 |
| IVF | 倒排文件索引 | 可通过探测桶数平衡速度与召回 | 需要训练聚类 | 大规模数据 |
| PQ | 乘积量化 | 大幅压缩向量 | 会损失精度 | 内存受限的超大规模数据 |
| IVF-PQ | 倒排文件加乘积量化 | 兼顾分桶和压缩 | 参数多、调优复杂 | 超大规模和成本敏感场景 |

Faiss 官方建议根据是否需要精确结果、内存预算、搜索次数和数据规模选择索引；HNSW 的 `efSearch` 与 IVF 的 `nprobe` 都用于调节速度和召回率的权衡。[Faiss 索引选型指南](https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index)

### 5.5 向量数据库怎么选

向量数据库不是只比较“向量搜索速度”。还应比较：

- Metadata Filter（元数据过滤）能力；
- 关键词与向量混合检索；
- 数据更新、删除和一致性；
- 分片、副本、备份和灾难恢复；
- 多租户、权限和审计；
- 本地部署、托管服务和成本；
- 已有技术栈与团队运维能力。

常见选型思路：

| 场景 | 可优先考虑的类别 |
| --- | --- |
| 已使用 PostgreSQL，规模中小 | PostgreSQL 向量扩展 |
| 已使用搜索引擎并需要 BM25 | 支持向量的全文搜索引擎 |
| 大规模原生向量检索 | Milvus、Qdrant 等向量数据库 |
| 单机实验或算法研究 | Faiss 等向量检索库 |
| 希望减少运维 | 托管向量服务 |

没有“生产环境统一首选”。例如，过滤条件与 HNSW 的结合本身就需要专项设计，Qdrant 也明确区分 Payload Index（载荷索引）和 Filterable HNSW（可过滤 HNSW）。[Qdrant 索引文档](https://qdrant.tech/documentation/manage-data/indexing/)

## 6. Query Understanding（查询理解）

### 6.1 为什么原始问题不一定适合直接检索

用户会省略上下文、使用口语、混合多个问题或只输入一个缩写。查询理解的目标是让检索更准确，但不能擅自改变实体、时间、否定条件和权限范围。

### 6.2 Query Rewriting（查询改写）

将对话中的指代补全，或把口语问题改为更明确的检索表达。例如：

```text
原问题：它去年有什么变化？
结合对话改写：产品 A 在 2025 年的价格政策有哪些变化？
```

应同时记录原问题和改写结果，以便排错。错误改写可能让后续检索完全偏离。

### 6.3 Multi-Query（多查询扩展）

从同一问题生成多个表达或角度，分别检索后融合。适合多义、复杂或召回不足的问题。缺点是成本增加、重复结果增多，也可能引入偏题查询。

### 6.4 HyDE（假设文档嵌入）

HyDE（Hypothetical Document Embeddings，假设文档嵌入）先让模型生成一段“可能的目标文档”，再对该文本生成向量并检索真实资料。原论文强调，假设文档本身可能包含错误细节，它只是用于在向量空间中寻找真实文档，不应直接作为答案证据。[HyDE 论文](https://arxiv.org/abs/2212.10496)

因此 HyDE 应保留原始 Query 检索通道，并通过本领域评测决定是否启用。

### 6.5 Query Decomposition（查询分解）

把多跳问题拆成依赖明确的子问题：

```text
问题：A 公司现任 CEO 曾任职的上一家公司采用什么休假制度？

子问题 1：A 公司现任 CEO 是谁？
子问题 2：此人上一家公司是哪家？
子问题 3：该公司的休假制度是什么？
```

每个中间结论都要保存证据，防止第一步错误继续传播。

### 6.6 Step-Back Prompting（退一步提问）

先检索上位概念或背景知识，再处理具体问题。它适合需要领域原理的问题，但不适合精确 ID 查询；对错误码和条款号应优先保留原始字符串。

## 7. Retrieval（检索）、Fusion（融合）与 Rerank（重排序）

### 7.1 Sparse Retrieval（稀疏检索）

稀疏检索基于词项和倒排索引，典型方法是 BM25（Best Matching 25，经典关键词相关性算法）。它综合 TF（Term Frequency，词频）、IDF（Inverse Document Frequency，逆文档频率）和文档长度进行排序。

擅长：

- 错误码、设备号和发票 ID；
- 人名、产品名和专业缩写；
- 法规条款号和代码符号；
- 必须精确出现的词。

不擅长：同义表达、口语改写和无共同关键词的语义匹配。

SPLADE（Sparse Lexical and Expansion，稀疏词汇扩展）等学习型稀疏模型会扩展相关词项，但本质上仍输出可用于倒排检索的稀疏表示。

### 7.2 Dense Retrieval（密集检索）

密集检索用 Embedding 表达语义，擅长同义词、口语化和概念相似。缺点是可能“过度理解”：查询“Apple 股价”时，某些模型可能把水果内容也判为相近；对随机字符串和精确编号也不稳定。

### 7.3 Hybrid Search（混合检索）

生产系统通常把稀疏与密集检索作为两个互补通道：

```text
                 ┌─ BM25 候选
用户 Query ──────┤
                 └─ 向量候选
                       ↓
                  去重与融合
                       ↓
                    Rerank
```

Elastic 官方文档也推荐用 RRF 组合全文与向量检索。[Elastic 混合检索文档](https://www.elastic.co/docs/solutions/search/hybrid-search)

### 7.4 RRF（倒数排名融合）

不同检索器的原始分数不在同一尺度上，直接相加往往不合理。RRF（Reciprocal Rank Fusion，倒数排名融合）只使用结果排名：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

- `d`：某个文档；
- `rank_i(d)`：文档在第 i 路结果中的名次；
- `k`：减弱高位名次差异的常数。

RRF 的优势是无需先校准 BM25 与向量分数。它不是完全“无需调参”：候选窗口、`k` 和各通道召回数量仍需根据评测调整。[Elastic RRF 参考](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

有充足标注数据时，也可以使用归一化后的线性加权或 LTR（Learning to Rank，学习排序）。

### 7.5 Reranker（重排序模型）

第一阶段召回追求 Recall（召回率），Reranker 追求前几名的 Precision（精确率）。Cross-Encoder（交叉编码器）把 Query 和候选文档一起输入模型，能进行细粒度交互判断：

- 标题是否相关但正文无答案；
- 实体、时间和版本是否正确；
- 文档只是提到关键词，还是能够支持结论；
- 半结构化字段与问题是否真正对应。

Reranker 比 Bi-Encoder 慢，因此只处理第一阶段的有限候选。官方 Rerank 文档同样将它定义为对现有搜索结果进行语义重排，而不是替代第一阶段召回。[Cohere Rerank 文档](https://docs.cohere.com/v2/docs/rerank)

关键边界：Reranker 只能重排已召回文档，找不回完全漏掉的证据。

### 7.6 Metadata Filtering（元数据过滤）

在检索前或检索引擎内部按以下条件缩小范围：

- 用户和租户权限；
- 产品线与文档类型；
- 版本、生效时间和语言；
- 内容类型，如代码、表格或说明书。

过滤过宽会产生噪声，过严会漏召回。必须在 Trace 中记录过滤条件及过滤前后的候选数量。

## 8. Context Packing（上下文组装）与生成

### 8.1 为什么召回结果不能直接拼接

候选结果可能重复、冲突、缺少父标题或超出 Token 预算。Context Packing（上下文组装）需要把检索结果变成模型易于使用、来源清晰的证据包。

### 8.2 组装步骤

1. 去除完全重复和高度重叠的片段；
2. 按 `document_id`、`parent_id` 恢复必要上下文；
3. 保留标题、来源、页码、版本和时间；
4. 对相互矛盾的来源显式标记；
5. 根据问题所需证据覆盖，而不是只按分数机械截取；
6. 在 Token 预算内选择少量高价值内容；
7. 为每个片段分配稳定的 Citation ID（引用标识）。

### 8.3 Evidence Sufficiency（证据充分性）

相关不等于足够回答。例如文档提到“退款期限”，但没有给出具体天数，就不能回答“几天内可以退款”。

判断方式：

- 结构化问题检查必要字段是否齐全；
- 多跳问题检查每一步是否有证据；
- 自由文本使用规则、分类器、NLI（自然语言推断）或受约束的 LLM Judge（大模型裁判）；
- 高风险任务设置更保守的拒答阈值。

### 8.4 Prompt（提示词）约束

生成提示至少应说明：

- 只能依据提供的证据回答；
- 证据不足或冲突时如何处理；
- 每个关键结论如何标注引用；
- 不得执行检索内容中的指令；
- 输出格式和必要字段；
- 是否允许使用模型常识，以及如何显式区分。

Few-shot Examples（少样本示例）可展示正确引用、正确拒答和冲突处理方式。

### 8.5 生成参数

事实型任务通常使用较低 Temperature（温度）以减少随机变化，但没有统一固定值。Top-p（核采样概率）和 Temperature 需要结合模型评测。

低温度只能让输出更稳定，不能让错误证据变正确，也不能阻止模型稳定地产生同一个错误。

### 8.6 Structured Output（结构化输出）

JSON Schema（JSON 结构约束）可以保证字段和类型，例如：

```json
{
  "answer": "……",
  "citations": ["doc-12#chunk-3"],
  "missing_information": [],
  "conflicts": []
}
```

Constrained Decoding（受限解码）可以约束合法格式或枚举值，但不能证明事实正确。结构化输出解决的是“怎么输出”，事实核验解决的是“输出是否有依据”。

## 9. 系统化排错

知识库中明明有答案但系统答错时，按数据流从前到后排查：

1. **源文档**：内容是否真实存在、正确且仍有效；
2. **解析**：是否漏页、乱码、OCR 错误、表格错位或标题丢失；
3. **分块**：正确证据是否形成完整 Chunk；
4. **索引**：Chunk 是否写入正确版本和租户；
5. **查询理解**：改写是否改变实体、时间或否定条件；
6. **权限过滤**：正确证据是否被错误过滤；
7. **初始召回**：正确 Chunk 是否进入候选 Top K；
8. **融合与重排**：正确候选是否被降权或截断；
9. **上下文组装**：证据是否真正进入最终 Prompt；
10. **生成**：模型是否忠实使用证据；
11. **生成后校验**：检测器是否误杀正确答案。

### 9.1 Oracle Context（理想上下文）对照实验

把人工确认的正确证据直接交给模型：

- 仍然答错：重点排查 Prompt、模型和生成后处理；
- 能够答对：重点排查解析、检索、排序和上下文组装。

这是隔离检索问题与生成问题的高效方法。

### 9.2 必须保存的 Trace

- 原始 Query 和改写 Query；
- 身份、租户、ACL 和 Metadata 过滤；
- 每路召回候选、分数和排名；
- 融合与 Rerank 前后结果；
- 最终上下文及截断原因；
- 模型、Prompt 和索引版本；
- 答案、引用、拒答和声明核验结果；
- 各阶段延迟、Token、费用和异常。

## 10. Hallucination（幻觉）治理

### 10.1 先区分两类错误

- **Factual Error（事实性错误）**：检索内容错误、过期、冲突或无关；
- **Faithfulness Hallucination（忠实性幻觉）**：证据正确，但模型添加、篡改或忽略了证据。

前者主要治理数据和检索，后者主要治理生成和校验。

### 10.2 检索前治理

- 清洗重复和过期文档；
- 保存来源、版本和生效时间；
- 修复解析和分块；
- 查询改写时保护实体、编号、时间和否定词；
- 为权限与内容类型建立可靠元数据。

### 10.3 检索中治理

- 使用混合检索避免单一路径盲区；
- 用 Reranker 提升 Top N 证据质量；
- 对多跳问题进行查询分解或多轮检索；
- 对版本、权限和领域做前置过滤；
- 证据不足时触发补检索或拒答。

### 10.4 生成时治理

- 只允许基于证据的关键结论；
- 强制关键事实附带引用；
- 证据不足或冲突时输出“不足以回答”；
- 使用结构化字段表达缺失信息与冲突；
- 不把检索内容中的指令当作系统指令。

### 10.5 生成后治理

- Atomic Claim Verification（原子声明核验）；
- NLI（自然语言推断）忠实性检测；
- Citation Verification（引用核验）；
- 业务规则、数值、单位和 Schema 校验；
- 失败后删除无依据内容、重新检索、重生成或转人工。

### 10.6 高风险任务的纵深防御

高风险场景不应依赖一个模型分数：

```text
数据治理
  -> 权限过滤
  -> 检索与证据判断
  -> 受约束生成
  -> 声明与业务规则校验
  -> 人工审批或确定性执行器
```

模型自报的 Confidence（置信度）不是经过校准的正确率。自动执行阈值必须用本领域标注数据校准，并结合操作风险。

## 11. 自动幻觉检测

### 11.1 有检索证据：优先做声明级核验

先把答案拆成只包含一个事实的 Atomic Claims（原子声明），再逐条判断：

- **Supported（有支持）**：证据能够推出该声明；
- **Contradicted（有矛盾）**：证据明确否定该声明；
- **No Evidence（无证据）**：证据没有提到该声明。

`No Evidence` 可能表示召回不足，`Contradicted` 表示生成内容与证据冲突，二者的修复方式不同。

### 11.2 NLI（自然语言推断）

NLI 把证据作为 Premise（前提），把声明作为 Hypothesis（假设），判断蕴含、矛盾或中立。它适合做低成本忠实性检查，但只能判断“回答是否忠于上下文”，不能判断上下文本身是否客观正确。

### 11.3 Citation Verification（引用核验）

需要验证四件事：

1. 引用 ID 是否真实存在；
2. 用户是否有权访问；
3. 引用版本是否正确；
4. 引用正文是否支持对应结论。

“答案带引用”不等于“引用正确”。

### 11.4 Black-box Detection（黑盒检测）

无法读取模型内部状态时，可使用：

- **SelfCheckGPT（自一致性检测）**：对同一问题多次采样，比较事实一致性；
- **LLM-as-Judge（大模型裁判）**：让另一个模型根据问题、证据和答案打分；
- **External Verification（外部验证）**：用数据库、计算器或权威事实源检查可验证字段。

SelfCheckGPT 的思想是：模型掌握某个事实时，多次采样通常更一致；不确定时更容易互相矛盾。[SelfCheckGPT 论文](https://arxiv.org/abs/2303.08896)

边界：一致性低只能说明不稳定，一致性高也可能是模型稳定地犯错。LLM Judge 自身也需要用人工标注集评测。

### 11.5 White-box Detection（白盒检测）

自部署模型可以读取内部信号：

- Token Probability（词元概率）；
- Semantic Entropy（语义熵）；
- Hidden State（隐藏层状态）；
- Attention Pattern（注意力模式）；
- Linear Probe（线性探针）。

容易误解的几个概念：

- 不存在跨所有模型固定编号的“幻觉注意力头”；
- FFN（Feed-Forward Network，前馈神经网络）是 Transformer 每层中的非线性变换模块，不等于事实数据库；
- Linear Probe 是在隐藏层向量上训练的轻量分类器，它识别统计风险模式，不是直接读取事实真假；
- 模型、版本和领域改变后，检测器通常需要重新标定。

### 11.6 生产选型

| 场景 | 推荐主方案 | 补充方案 |
| --- | --- | --- |
| 有检索上下文、闭源模型 | 原子声明 + NLI + 引用核验 | LLM Judge 处理复杂样本 |
| 无外部证据、闭源模型 | 外部事实源或 LLM Judge | 多次采样一致性 |
| 自部署开源模型 | 外部证据核验 | 白盒不确定性信号 |
| 高风险生产任务 | 自动检测 + 确定性规则 + 人工复核 | 多模型交叉检查 |

检测器本身也要评估 Precision（精确率）、Recall（召回率）、误杀率、漏检率、延迟和成本。

## 12. Advanced RAG（高级 RAG）

### 12.1 Corrective RAG（纠错式 RAG）

CRAG（Corrective Retrieval-Augmented Generation，纠错式检索增强生成）在召回后增加 Retrieval Evaluator（检索评估器），根据证据质量决定直接回答、修正检索或扩展数据源。原论文还使用“分解再重组”过滤文档中的无关内容。[CRAG 论文](https://arxiv.org/abs/2401.15884)

```text
检索
  -> 评估证据质量
       ├─ 足够：生成
       ├─ 模糊：改写/扩大召回
       └─ 不相关：切换数据源或拒答
```

### 12.2 Self-RAG（自反思式 RAG）

Self-RAG（Self-Reflective Retrieval-Augmented Generation，自反思式检索增强生成）让模型学习何时检索、证据是否相关，以及生成结果是否被证据支持。论文中的 Reflection Tokens（反思词元）是训练设计的一部分，不等同于简单地在 Prompt 中要求“反思一下”。[Self-RAG 论文](https://arxiv.org/abs/2310.11511)

### 12.3 RAPTOR（树状递归检索）

RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval，面向树状检索的递归摘要处理）对文本块进行聚类和递归摘要，形成从细节到高层概括的树。查询时可以从不同抽象层检索，适合长文档的整体理解和多步问题。[RAPTOR 论文](https://arxiv.org/abs/2401.18059)

### 12.4 何时需要这些方案

- 召回质量波动明显：考虑 CRAG；
- 不同问题是否需要检索差异很大：考虑 Self-RAG 思路或显式路由；
- 长文档需要跨层级理解：考虑 RAPTOR 或层次化摘要；
- 基础召回本身很差：先修复数据、分块和混合检索。

## 13. GraphRAG（图增强检索生成）

### 13.1 传统文本 RAG 的边界

向量检索擅长找“与问题相似的局部片段”，但以下问题没有一个明显的局部片段：

- 整个知识库的主要主题是什么；
- 多个实体之间存在怎样的关系；
- 答案需要跨多份文档进行 A → B → C 推理；
- 同一实体在不同文档中的描述需要合并。

### 13.2 GraphRAG 索引过程

Microsoft GraphRAG 的标准索引流程会从原文抽取 Entity（实体）、Relationship（关系）和 Claim（声明），执行 Community Detection（社区发现），生成多层 Community Report（社区报告），同时保留 Text Unit（文本单元）和向量表示。[GraphRAG 索引文档](https://microsoft.github.io/graphrag/index/overview/)

```text
原始文本
  -> 实体、关系和声明抽取
  -> 实体消歧与图构建
  -> 社区发现
  -> 多层社区摘要
  -> 图、文本块和向量联合索引
```

### 13.3 Local Search（本地搜索）

本地搜索适合围绕具体实体的问题。它先把 Query 映射到相关实体，再扩展关系、相邻实体、社区报告和原始文本块，最后在 Token 预算内组装上下文。[GraphRAG 本地搜索](https://microsoft.github.io/graphrag/query/local_search/)

### 13.4 Global Search（全局搜索）

全局搜索适合“整个数据集的主要主题是什么”这类问题。它在社区报告上执行 Map-Reduce（映射归约）：先让多个报告分别产生中间结论，再汇总为最终答案。它比普通局部检索消耗更多模型资源。[GraphRAG 全局搜索](https://microsoft.github.io/graphrag/query/global_search/)

### 13.5 DRIFT Search（动态推理与推断搜索）

DRIFT（Dynamic Reasoning and Inference with Flexible Traversal，动态推理与灵活遍历）把社区信息用于扩展本地查询，在局部问题中获得更广的起点和后续问题。它位于本地搜索与全局搜索之间。[GraphRAG 查询概览](https://microsoft.github.io/graphrag/query/overview/)

### 13.6 GraphRAG 的代价

- Ontology（本体）和实体类型设计；
- 实体抽取、消歧和关系质量；
- LLM 索引成本；
- 图与原文的增量更新；
- 图查询、文本检索和引用的统一；
- 更复杂的评测。

Microsoft 官方也提示 GraphRAG 索引可能消耗大量 LLM 资源，应先用小数据和低成本模型验证。[GraphRAG 入门文档](https://microsoft.github.io/graphrag/get_started/)

### 13.7 什么时候用

适合：关系密集、多跳、跨文档和全局总结。

不适合默认使用：FAQ、制度条款、错误码和单文档事实定位。此类问题先做好结构化分块、混合检索和 Rerank，通常更直接。

## 14. Agentic RAG（智能体式检索增强生成）

### 14.1 核心思想

Agentic RAG 不再把检索流程写死，而是让 Agent 根据目标和中间结果决定：

- 是否需要检索；
- 使用 BM25、向量库、SQL、图谱、API 还是网络搜索；
- 是否拆分或改写问题；
- 证据不足时是否继续；
- 何时停止并返回答案。

### 14.2 核心组件

- Router（路由器）：选择数据源和检索策略；
- Planner（规划器）：拆分问题和依赖；
- Tool Use（工具使用）：调用搜索、数据库和业务 API；
- State（状态）：保存问题、证据和中间结论；
- Evaluator（评估器）：判断证据是否足够；
- Stop Condition（停止条件）：限制轮数、时间、Token 和费用。

### 14.3 风险

- 多次模型调用增加延迟和成本；
- 查询改写和工具选择可能偏离目标；
- 循环可能无法停止；
- 外部搜索与工具扩大权限和注入风险；
- 多轮证据更难追踪。

生产系统应使用确定性 Workflow（工作流）控制权限、预算和关键状态，仅把无法预先穷举的语义决策交给 Agent。

### 14.4 与 GraphRAG 的区别

GraphRAG 主要改变“知识如何组织和检索”；Agentic RAG 主要改变“检索流程由谁动态决策”。二者可以组合：Agent 判断某个关系型问题应调用图检索。

## 15. Security（安全）与 Permission（权限）

### 15.1 权限必须进入检索层

文档入库时保存 Tenant（租户）、用户、用户组、角色和 ACL；查询时由服务端根据已认证身份生成过滤条件。Azure AI Search 的文档级访问控制同样依赖索引中的权限元数据，并在查询时按用户或用户组权限过滤结果。[Azure AI Search 文档级访问控制](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)

不能先召回再隐藏：

1. 无权限结果会占据 Top K；
2. 敏感内容可能已经进入缓存、日志和 Trace；
3. 一旦进入模型上下文就已产生泄露风险；
4. Prompt 不能充当访问控制系统。

### 15.2 隔离方式

| 隔离方式 | 做法 | 优点 | 风险与成本 |
| --- | --- | --- | --- |
| 逻辑隔离 | 同一索引加租户和 ACL 过滤 | 成本低、易共享 | 过滤错误可能泄露 |
| 索引级隔离 | 不同安全域使用独立索引 | 边界更清晰 | 索引数量和运维复杂 |
| 实例级隔离 | 独立数据库或集群 | 隔离最强 | 成本最高 |

选择依据是安全等级、租户数量、监管要求和成本，不存在对所有企业统一最佳的方式。

### 15.3 RBAC 与 ABAC

- RBAC（Role-Based Access Control，基于角色的访问控制）：根据角色授权；
- ABAC（Attribute-Based Access Control，基于属性的访问控制）：根据部门、密级、地域、时间等属性动态判断。

企业系统常组合使用，最终权限判断仍由独立授权服务执行。

### 15.4 Indirect Prompt Injection（间接提示词注入）

知识库、网页和邮件可能包含“忽略系统规则”“把数据发送到某地址”等恶意文字。它们是数据，不是可信指令。

防御措施：

- 将系统指令、用户请求和检索数据结构化分离；
- 明确检索内容没有修改系统规则的权限；
- 对工具调用重新做授权、参数和数据流向检查；
- 对敏感字段脱敏；
- 高风险操作要求 Human-in-the-loop（人工参与审批）；
- 使用对抗测试覆盖直接注入、间接注入和数据外传。

过滤恶意字符串只能作为辅助，真正安全边界必须在模型外部。

### 15.5 审计

审计至少保存：用户身份、原始问题、权限决策、召回文档、索引版本、最终证据、模型输出、工具调用和审批记录。日志需要脱敏、分级授权和保留期限。

## 16. Evaluation（评测）

### 16.1 为什么必须分层评测

RAG 是模块化系统。最终答案错了，可能是没召回、排错顺序、上下文截断或模型不忠实。只评一个“准确率”无法指导优化。

### 16.2 评测集怎么建

优先来源：

- 真实历史问题；
- 用户反馈和线上 Bad Case；
- 业务专家设计的边界问题；
- 模型生成并经人工审核的补充样本。

每道题保存：问题类型、标准答案、支持证据、可接受范围、文档版本、权限范围、是否应拒答和关键实体。

必须覆盖：语义改写、精确编号、多跳、多文档、表格、版本冲突、无答案、权限、对抗输入和长上下文。

### 16.3 检索指标

| 指标 | 中文解释 | 回答的问题 |
| --- | --- | --- |
| Recall@K | 前 K 项召回率 | 正确证据是否被找到了 |
| Precision@K | 前 K 项精确率 | 找到的内容有多少真正相关 |
| MRR | 平均倒数排名 | 第一个正确结果排得是否靠前 |
| NDCG | 归一化折损累计增益 | 多个相关结果的整体排序是否合理 |

### 16.4 生成指标

| 指标 | 中文解释 |
| --- | --- |
| Answer Correctness | 答案正确性 |
| Faithfulness / Groundedness | 忠实度 / 证据支撑度 |
| Answer Relevancy | 答案相关性 |
| Citation Correctness | 引用正确性 |
| Refusal Accuracy | 拒答准确性 |

### 16.5 系统指标

- 端到端任务成功率；
- P50、P95、P99 延迟和 Time to First Token（首词元时间）；
- 各阶段错误率、超时和重试；
- Embedding、Rerank 和生成成本；
- 索引新鲜度和权限同步延迟；
- 用户满意度、转人工率和纠错率。

### 16.6 评测框架

RAGAS 提供无需每项都依赖人工 Ground Truth（标准答案）的 RAG 评测思路，覆盖检索上下文和生成质量。[RAGAS 论文](https://arxiv.org/abs/2309.15217)

RAGChecker 强调分别诊断检索与生成模块，并使用更细粒度指标分析系统权衡。[RAGChecker 论文](https://arxiv.org/abs/2408.08067)

自动指标不能完全替代人工评审。LLM-as-Judge 需要做校准，并报告与人工判断的一致性。

### 16.7 正确比较方案

1. 开发集用于调参，独立测试集用于最终比较；
2. 新旧方案使用相同文档、问题、权限和模型版本；
3. 同时报告总体结果与问题类型切片；
4. 报告质量、延迟和成本，而不是只报准确率；
5. 使用消融实验确认每个组件的实际贡献；
6. 离线通过后再进行小流量 A/B Test（对照实验）。

## 17. Production Operations（生产运维）

### 17.1 增量更新

为文档保存 ID、版本、更新时间和 Content Hash。通过文件事件、消息队列或 CDC（Change Data Capture，变更数据捕获）监听新增、修改、删除、过期和撤权。

只重新处理发生变化的文档；块级哈希未变化时可复用 Embedding。

### 17.2 正确的版本发布

不要先删除旧索引，再逐条写入新索引。这样会产生空窗和混合版本。

```text
构建新版本索引
  -> 完整性检查
  -> 抽样检索回归
  -> 原子切换 Active Alias（活动别名）
  -> 保留旧版本供回滚
  -> 稳定后异步清理
```

Elasticsearch 的 Alias API（别名接口）支持在一个原子操作中移除旧索引并添加新索引，从而实现无停机切换。[Elastic Alias 文档](https://www.elastic.co/guide/en/elasticsearch/reference/current/aliases.html)

小规模文档更新也要保证同一次查询使用一致的文档版本和索引版本。

### 17.3 可靠性

- 索引任务使用 Idempotency Key（幂等键）；
- 对网络和限流等临时错误有限重试；
- 无法处理的事件进入 DLQ（Dead Letter Queue，死信队列）；
- 保存失败原因、重试次数和处理版本；
- 定期检查孤儿 Chunk、重复向量和元数据缺失；
- 保留上一有效索引以快速回滚。

### 17.4 缓存

可缓存 Query Embedding（查询向量）、只读检索结果、Rerank 结果或最终答案，但缓存键至少应包含：

- 用户权限或可见范围；
- Query 与过滤条件；
- 文档和索引版本；
- Embedding、Rerank、生成模型版本；
- Prompt 版本和有效期。

权限变化或文档撤权时必须让相关缓存失效。

### 17.5 性能与成本

- 离线 Embedding 批量处理；
- BM25 与向量通道并行召回；
- 控制各路候选数量和 Rerank 窗口；
- 去重后再进入模型；
- 简单问题用轻量模型，复杂问题升级；
- 流式输出只能降低感知延迟，不能降低完整答案生成时间；
- 量化和压缩必须用召回率回归验证，不能只看显存或内存下降。

### 17.6 可观测性与告警

监控：

- 索引积压、更新延迟和失败率；
- 召回率代理指标、空结果率和低分结果率；
- Rerank 前后排序变化；
- 拒答率、引用失败率和忠实度抽样；
- P95/P99、Token、费用和缓存命中率；
- 权限过滤异常和敏感数据访问。

质量指标通常需要标注或 Judge，不能把 Context Recall 这类离线指标简单地声称为每次线上请求的“实时真值”。

## 18. Multimodal RAG（多模态检索增强生成）

### 18.1 为什么纯 OCR 不够

图表、页面布局、字体、公式和表格结构本身包含信息。只抽取文本可能破坏视觉关系。

### 18.2 常见路径

- 图片：文本到图像联合 Embedding；
- 视觉文档：页面图片多向量检索；
- 表格：结构化索引、SQL 或专门的 Table Retrieval（表格检索）；
- 代码：符号检索 + BM25 + Code Embedding（代码嵌入）；
- 视频：语音转写、关键帧、时间戳和片段检索；
- 数据库：Schema Linking（模式链接）后生成受控 SQL。

ColPali 展示了直接把文档页面图像编码成多向量，并通过 Late Interaction（后期交互）完成视觉文档检索的路线。[ColPali 论文](https://arxiv.org/abs/2407.01449)

### 18.3 设计原则

不要把所有数据强行转成同一种文本 Chunk。应根据数据形态选择检索器，再在结果层做统一引用和权限管理。

## 19. 场景选型与落地路线

### 19.1 场景选型

| 场景 | 推荐起点 | 主要增强 |
| --- | --- | --- |
| 企业制度和手册问答 | 结构分块 + 混合检索 + Rerank | 权限、版本、引用和拒答 |
| 错误码、条款号和产品 ID | BM25 为主的混合检索 | 字段权重、精确过滤 |
| 用户表达模糊 | 混合检索 | 查询改写、多查询扩展 |
| 长文档整体理解 | 层次化父子块 | RAPTOR 或摘要树 |
| 跨文档关系与全局主题 | 文本 RAG 基线 | GraphRAG |
| 多数据源复杂任务 | 确定性 Workflow | Agentic RAG |
| 表格聚合和精确计算 | SQL / 结构化工具 | RAG 负责 Schema 和解释 |
| 图表与复杂版面 | OCR + 文本检索基线 | 视觉文档检索 |
| 高风险业务 | 证据核验 + 规则 | 人工审批与审计 |

### 19.2 分阶段落地

#### 第一阶段：建立可解释基线

- 正确解析一类核心文档；
- 结构化分块和 Metadata；
- 建立 BM25 与向量检索基线；
- 返回引用；
- 保存完整 Trace；
- 建立 50～200 条高质量评测样本。

#### 第二阶段：提高检索质量

- 混合检索与 RRF；
- Reranker；
- 父子块和上下文组装；
- 按文档类型调参；
- 权限与版本前置过滤。

#### 第三阶段：治理幻觉

- Evidence Sufficiency 与拒答；
- 原子声明和引用核验；
- NLI 或 LLM Judge；
- Bad Case 回灌和持续回归。

#### 第四阶段：生产化

- 增量更新和索引原子切换；
- 缓存、并发、成本和容量规划；
- 监控、告警、审计与回滚；
- 间接提示词注入和越权测试。

#### 第五阶段：按需引入高级架构

- 长文档层次问题：RAPTOR；
- 检索质量动态波动：CRAG；
- 全局与关系问题：GraphRAG；
- 动态多工具任务：Agentic RAG；
- 视觉文档：Multimodal RAG（多模态 RAG）。

### 19.3 十条核心认知

1. 数据质量和解析质量决定 RAG 上限。
2. Chunk Size 没有通用最佳值，结构边界通常比固定长度更重要。
3. BM25 与向量检索互补，混合检索是可靠基线，不是绝对教条。
4. Reranker 提高候选排序，不能找回漏召回证据。
5. 相关性不等于证据充分性。
6. Structured Output 约束格式，不能保证事实正确。
7. 低 Temperature 降低随机性，不能消除幻觉。
8. 权限必须在检索阶段由服务端强制执行。
9. GraphRAG 和 Agentic RAG 只应解决基础 RAG 无法经济解决的问题。
10. 没有评测集、Trace 和版本管理，就无法持续优化生产 RAG。
