# Multi-Agent（多智能体）系统学习指南

> 上位导航：[AI Agent 知识体系](README.md)

> 多智能体的价值来自任务分解、并行探索、专业上下文和权限隔离，而不是简单增加 Agent 数量。它会放大计算能力，也会放大协调、成本、状态冲突和错误传播问题。

## 0. 什么时候需要多智能体

适合：

- 任务可拆成多个相对独立的方向，存在真实并行收益；
- 不同子任务需要不同模型、工具、指令或权限；
- 单个上下文无法容纳全部探索过程；
- 需要独立生成与审查、对抗式验证或多方案比较；
- 团队边界、数据域或合规边界要求隔离。

不适合：

- 简单顺序任务；
- 子任务高度依赖、频繁通信；
- 共享状态强耦合且要求强一致；
- 单智能体配合工具即可稳定完成；
- 没有评测证明质量收益大于延迟和成本。

## 1. 多智能体基础组成

```text
User Goal（用户目标）
  → Orchestrator / Manager（编排者 / 管理者）
      ├─ Specialist A（专业智能体 A）
      ├─ Specialist B（专业智能体 B）
      └─ Specialist C（专业智能体 C）
  → Aggregator / Judge（聚合器 / 裁决者）
  → Verified Outcome（已验证结果）
```

除了 Agent，还必须有：任务协议、状态所有权、通信边界、预算、失败策略、聚合规则和可观测性。

## 2. 常见编排模式

### 2.1 Manager-as-Tools（管理者调用子智能体）

管理者保持对用户会话和最终答案的控制，把专业 Agent 当工具调用。

适合：需要统一口径、综合多个专家结果、集中执行 Guardrail（护栏）。缺点是管理者成为上下文与性能瓶颈。

### 2.2 Handoff（任务移交）

路由 Agent 把控制权交给专业 Agent，后者成为当前活跃者并直接响应。

适合：客服分流、专业领域会话。风险是上下文传递过多或过少、权限随移交泄露、用户不知道当前由谁负责。

### 2.3 Orchestrator-Workers（编排者—工作者）

编排者动态拆分任务，多个 Worker 并行工作，再汇总。适合开放研究、代码库分析和多来源搜索。

### 2.4 Pipeline（流水线）

Planner（规划者）→ Executor（执行者）→ Reviewer（审查者）。结构清晰，但上游错误会传播，下游也可能无依据地推翻正确结果。

### 2.5 Debate / Voting（辩论 / 投票）

多个 Agent 独立提出答案，再投票或由 Judge（裁决者）选择。只在答案可比较、错误相对独立且评测证明有效时使用。多个同质模型可能共享同一偏差，投票不保证真相。

### 2.6 Blackboard（黑板模式）

多个 Agent 读写共享工作区。适合复杂协作，但必须控制 Schema、所有权、版本和冲突，不能把一段共享聊天记录当作可靠状态。

## 3. LLM 编排与代码编排

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 代码编排 | 确定、低成本、可测试 | 灵活性有限 | 已知路由、固定依赖、强规则 |
| LLM 编排 | 能理解开放目标并动态拆分 | 不确定、成本高、需防循环 | 子任务无法预先枚举 |
| 混合编排 | 灵活与控制兼顾 | 设计复杂 | 多数生产场景 |

推荐：代码定义允许的拓扑、权限、预算和汇合点；LLM 在边界内决定子任务内容、选择专业能力和必要的重规划。

## 4. Task Decomposition（任务分解）

好的子任务应具备：

- 明确目标、输入、输出 Schema 和完成标准；
- 尽量减少对其他分支中间状态的依赖；
- 指定可用工具、数据范围和权限；
- 限定时间、Token、费用和最大步骤；
- 说明证据与来源要求；
- 指明失败时返回什么，而不是静默编造。

不要只传“帮我研究一下 X”。应传递结构化 Task Contract（任务契约）。

## 5. 通信与上下文隔离

### 5.1 传什么

传递目标、必要背景、约束、输入引用、输出契约和预算。默认不传完整父 Agent 历史，减少隐私泄露和上下文污染。

### 5.2 返回什么

子 Agent 返回：结论、证据、置信度、未解决问题、状态和资源消耗。长原始材料保存到 Artifact Store（产物存储），只传引用。

### 5.3 通信方式

- Synchronous Call（同步调用）：简单，适合短任务；会占用上游等待时间。
- Async Queue（异步队列）：适合长任务、重试和弹性伸缩。
- Event-driven（事件驱动）：适合松耦合，但更难追踪顺序和一致性。
- Shared Store（共享存储）：适合大产物，必须做权限和版本控制。

## 6. State Ownership（状态所有权）

多智能体最常见的问题不是“不会推理”，而是谁可以改什么。

推荐规则：

- Orchestrator 拥有全局任务状态和最终生命周期；
- 每个 Worker 只写自己的分支空间；
- 共享业务资源由单一服务或仲裁器执行写入；
- Aggregator 只读取分支结果并生成合并结果；
- 状态更新带版本、作者、时间和来源；
- 冲突必须有确定性策略或人工处理。

## 7. 聚合、冲突与事实核验

### 7.1 Aggregation（聚合）

聚合不只是拼接。应去重、对齐 Schema、比较来源、识别缺口、处理冲突并检查是否满足目标。

### 7.2 冲突策略

- 基于权威来源、时间、适用范围和证据强度排序；
- 对独立计算可重新执行或用确定性代码验证；
- 对主观结论保留多种观点并说明依据；
- 无法裁决时明确不确定性或交给人工。

### 7.3 Reviewer 的边界

Reviewer 必须有可执行的 Rubric（评分准则）和证据访问权限。一个没有新证据、只被要求“挑错”的模型不天然更可靠。

## 8. 容错与降级

- Partial Failure（部分失败）：允许汇总已完成分支，并清楚标记缺失。
- Timeout（超时）：取消或隔离慢分支，避免拖垮整体 Deadline。
- Retry（重试）：按子任务幂等重试，不重新启动全部系统。
- Reassignment（重新分配）：Worker 不可用时换能力相近者。
- Quorum（法定数量）：对必须收集多个结果的场景定义最低完成数。
- Graceful Degradation（优雅降级）：多智能体失败时回退单智能体、固定流程或人工。

子 Agent 失败不能只返回一句空答案，否则管理者可能误认为任务已完成。状态必须显式为 success、partial、failed 或 timed_out。

## 9. 多智能体安全

- 每个 Agent 使用独立最小权限，不继承管理者全部凭证；
- Handoff 时重新计算工具与数据权限；
- Agent 间消息视为不完全可信输入，防止 Compromised Agent（被攻陷智能体）传播恶意指令；
- 敏感数据按 Need-to-know（知悉必要）原则传递；
- 高风险共享工具由中央策略层与审批层控制；
- 限制 Agent 创建 Agent 的深度、数量和总预算；
- 所有委派、调用、状态更新与副作用可审计。

## 10. 成本与性能

多智能体成本近似为所有分支模型、工具、通信、重试和聚合之和。优化方法：

- 简单请求不启动多智能体；
- 先低成本分类，再决定并行宽度；
- 按子任务难度路由模型；
- 限制递归委派深度与每层 Fan-out（扇出）；
- 共享可复用检索结果，但不共享不必要的上下文；
- 早停低价值分支；
- 用评测找到边际收益递减点。

## 11. 多智能体评测

除最终任务成功率外，还需观察：

- Decomposition Quality（分解质量）；
- Routing / Assignment Accuracy（路由 / 分配准确率）；
- Coverage（覆盖度）与重复工作率；
- Communication Overhead（通信开销）；
- Conflict Resolution Accuracy（冲突解决准确率）；
- Partial Failure Recovery（部分失败恢复率）；
- 每个 Agent 的 Token、延迟、工具次数与贡献度；
- 单智能体基线对比。

Anthropic 的研究系统案例说明多智能体对可并行的广度型研究任务可能显著受益，但这是特定系统和内部评测结果，不能直接外推到所有业务。

## 12. 常见失败与排错

| 现象 | 根因 | 排查 |
|---|---|---|
| 多 Agent 反而更差 | 任务不可并行、重复工作、汇总损失 | 与单体基线比较，查看分支贡献 |
| 状态互相覆盖 | 无所有权、共享大对象 | 分支命名空间、版本控制、单写者 |
| 无限创建子 Agent | 无深度和预算限制 | 全局预算、最大扇出、递归检测 |
| 结果互相矛盾 | 来源不同、任务边界重叠 | 保留证据，确定性冲突策略 |
| 一个分支拖垮整体 | 同步等待、无 Deadline | 分支超时、取消、法定数量、降级 |
| Handoff 后越权 | 权限随上下文直接继承 | 每次移交重新授权并缩小工具集 |

## 13. 面试重点

### 13.1 什么时候用多智能体？

答题要点：存在可独立分解的任务、并行收益、专业工具/上下文或权限隔离需求，并且业务评测相对单体证明收益。不是复杂任务就默认多 Agent。

### 13.2 Manager-as-Tools 和 Handoff 有什么区别？

答题要点：前者由管理者保持会话控制、调用专家并汇总；后者把控制权交给专家直接处理。前者适合统一答案和集中护栏，后者适合专业分流和聚焦上下文。

### 13.3 多 Agent 怎样共享状态？

答题要点：全局状态由编排器所有，分支写自己的命名空间，共享业务副作用通过单一服务；使用版本控制、事件或合并节点，避免多个 Agent 修改同一自然语言对象。

### 13.4 如何处理部分失败？

答题要点：分支级超时与重试、显式状态、最低完成数、替代 Worker、聚合时标记缺失、回退单体或人工。副作用任务仍需幂等和补偿。

### 13.5 如何证明多智能体值得？

答题要点：与相同工具和模型预算下的单智能体、工作流基线比较任务成功率、覆盖率、延迟、总成本、安全性和稳定性，并分析每个分支的边际贡献。

## 14. 术语速查

| 英文 | 中文 | 含义 |
|---|---|---|
| Orchestrator | 编排者 | 分解、调度和汇总子任务的角色 |
| Manager-as-Tools | 管理者调用子智能体 | 管理者把专家 Agent 作为工具使用 |
| Handoff | 任务移交 | 将当前控制权交给另一个 Agent |
| Worker | 工作者 | 执行特定子任务的 Agent |
| Fan-out / Fan-in | 扇出 / 汇聚 | 并行分发任务和汇总结果 |
| Blackboard | 黑板模式 | 多 Agent 通过共享工作区协作 |
| Quorum | 法定数量 | 继续或裁决所需的最低结果数 |
| Task Contract | 任务契约 | 子任务输入、输出、约束和完成标准 |
