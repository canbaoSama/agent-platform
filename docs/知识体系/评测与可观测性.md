# Evaluation（评测）与 Observability（可观测性）系统学习指南

> 上位导航：[AI Agent 知识体系](README.md)

> 评测回答“系统是否做得好”，可观测性回答“这一次发生了什么、为什么”。二者必须共享任务标识、版本和轨迹，才能把线上失败转化为离线回归用例。

## 0. 为什么 Agent 更难评测

Agent 会多轮调用模型与工具、改变环境、动态调整路径。相同任务可能存在多条正确轨迹，也可能最终文本看似正确但真实副作用失败。因此不能只评最后一句答案。

需要区分：

- Transcript / Trajectory（记录 / 轨迹）：模型、工具、移交和中间状态的完整过程。
- Outcome（最终状态）：任务结束后真实环境发生了什么。
- Trial（试验）：同一个任务的一次独立运行。
- Task（任务样例）：输入、环境和成功标准。
- Grader（评分器）：对过程或结果打分的逻辑。
- Eval Harness（评测框架）：运行、记录、评分和汇总的基础设施。

## 1. 分层评测体系

### 1.1 模型层

指令遵循、分类、抽取、推理、结构化输出和安全拒绝。

### 1.2 组件层

- RAG：召回、重排、有据性和引用；
- Tool：候选召回、选择、参数、错误处理；
- Memory：写入、召回、冲突、遗忘和泄露；
- Router（路由器）：领域、模型、Agent 与风险分类。

### 1.3 轨迹层

是否调用必要工具、是否避免禁止动作、步骤是否重复、是否正确处理错误、是否在预算内终止。

### 1.4 结果层

用数据库、文件、API 状态或测试验证真实 Outcome。结果层通常比最终文本更可信。

### 1.5 系统层

端到端成功率、延迟、成本、可用性、安全事件、用户满意度和业务指标。

## 2. Grader（评分器）类型

### 2.1 Code-based Grader（代码评分器）

精确匹配、正则、Schema 校验、单元测试、静态分析、数据库状态检查。确定、便宜、可复现，能用代码判断时优先使用。

### 2.2 Model-based Grader（模型评分器）

适合相关性、完整性、表达质量和开放任务。必须提供清晰 Rubric（评分准则）、证据和反例，并定期与人工结果校准。避免让评分器知道被评方案名称，减少偏差。

### 2.3 Human Grader（人工评分器）

适合高风险、主观或评分器校准任务。成本高、速度慢，还需处理标注者一致性。

生产评测通常组合三类评分器，而不是寻找一个万能分数。

## 3. Capability Eval 与 Regression Eval

- Capability Eval（能力评测）：探索系统能解决多难的问题，初始通过率可以较低。
- Regression Eval（回归评测）：保护已经能稳定完成的能力，目标是接近全通过。

线上故障、用户投诉和人工审查样例应去敏后加入回归集。能力评测中成熟且稳定的样例可以转为回归集。

## 4. 数据集设计

评测集应覆盖：

- 常规主路径；
- 边界条件、歧义输入和缺失信息；
- 工具超时、部分失败、结果冲突；
- 多轮状态变化与用户反悔；
- Prompt Injection、越权和敏感数据；
- 长上下文、过期 Memory 与错误 RAG；
- 多 Agent 冲突、慢分支和重复副作用；
- 不应调用 Agent 或工具的简单请求。

按难度、领域、语言、租户、风险和失败类型分层报告，避免平均分掩盖关键风险。

## 5. 随机性与统计

同一 Task 应运行多个 Trial，报告均值、分布和置信区间，而不是只挑最好结果。上线比较要控制：模型版本、Prompt、工具、数据快照、采样参数和环境。

高风险动作不仅看平均成功率，还要看最坏情况与严重失败率。一次越权可能比一百次正常回答更重要。

## 6. Trace、Span、Log 与 Metric

| 信号 | 含义 | Agent 示例 |
|---|---|---|
| Trace | 一次端到端操作 | 一次用户任务 |
| Span | Trace 中一个有起止时间的步骤 | 模型生成、工具调用、Handoff |
| Log | 离散事件记录 | 参数校验失败、审批拒绝 |
| Metric | 可聚合数值 | 成功率、P95 延迟、Token、费用 |

OpenAI Agents SDK 的 Trace 可覆盖模型生成、工具调用、Handoff 和 Guardrail；OpenTelemetry（开放遥测）为生成式 AI 操作提供逐步演进的语义约定。标准仍在发展，落地时应锁定版本并保护敏感字段。

## 7. 建议记录的字段

- `trace_id`、`run_id`、`session_id`、`tenant_id`；
- Agent、模型、Prompt、工具、知识库和策略版本；
- 每步输入输出 Token、缓存 Token、延迟和费用；
- 工具候选集、选择、参数摘要、状态、重试和错误码；
- RAG 查询、文档 ID、分数和引用；
- Memory 候选、入选和写入决策；
- State 版本、Checkpoint、Handoff 和审批事件；
- 最终 Outcome 与各 Grader 分数。

不要默认记录完整 Prompt、工具参数和结果，其中可能含密钥、个人数据和业务机密。需要脱敏、采样、访问控制、保留期限和删除机制。

## 8. 核心指标

### 8.1 质量

- Task Success Rate（任务成功率）
- Groundedness（有据性）
- Tool Call Accuracy（工具调用准确率）
- Policy Compliance（策略遵循率）
- Human Escalation Precision（人工升级精确率）

### 8.2 可靠性

- Error / Timeout Rate（错误 / 超时率）
- Retry Recovery Rate（重试恢复率）
- Duplicate Side-effect Rate（重复副作用率）
- Checkpoint Resume Success（检查点恢复成功率）
- No-progress Loop Rate（无进展循环率）

### 8.3 性能与成本

- P50、P95、P99 端到端与分阶段延迟；
- 单成功任务总 Token 和总费用；
- 工具调用次数、并行宽度和缓存命中率；
- Cost per Successful Task（每个成功任务成本），比单次模型价格更有意义。

## 9. 从线上到离线的闭环

```text
线上 Trace / 用户反馈 / 告警
  → 失败分类与根因定位
  → 去敏并构造最小复现 Task
  → 加入回归评测
  → 修改模型、上下文、工具或运行时
  → 离线通过
  → Shadow / Canary（影子 / 金丝雀）验证
  → 分阶段发布与持续监控
```

评测是活资产，需要明确 Owner（所有者）、版本、变更审查和定期清理过时样例。

## 10. 系统化排错

1. 确认最终 Outcome，而不是先看最终文字。
2. 定位第一个偏离预期的 Span。
3. 判断是输入、上下文、模型决策、工具、状态还是策略错误。
4. 用固定数据和版本复现。
5. 构造最小失败用例和相邻反例。
6. 修改后跑组件与端到端回归。
7. 检查质量提升是否以延迟、成本或安全退化为代价。

## 11. 面试重点

### 11.1 如何评测 Agent？

答题要点：分模型、组件、轨迹、Outcome 和系统五层；结合代码、模型和人工评分器；同任务多次 Trial；同时评质量、可靠性、延迟、成本与安全。

### 11.2 为什么最终答案正确还可能评测失败？

答题要点：可能越权读取、调用禁止工具、重复扣款、碰巧猜对或成本超限。Agent 必须同时满足过程约束和真实最终状态。

### 11.3 LLM-as-a-Judge（大模型评分器）有哪些问题？

答题要点：存在位置、风格、自偏好和提示敏感性；不能判断自己看不到的真实状态。需要明确 Rubric、隐藏方案身份、多评分器或抽样、用人工和代码校准。

### 11.4 线上可观测性应记录什么？

答题要点：Trace 关联模型、工具、RAG、Memory、Handoff、Guardrail 和状态；记录版本、延迟、Token、费用、错误与 Outcome；敏感内容需脱敏、采样和访问控制。

### 11.5 怎样建立回归集？

答题要点：从需求、历史故障、用户反馈和对抗测试提取真实样例；定义可验证成功标准；按失败类型分层；每次修复把最小复现加入回归并长期维护。

## 12. 术语速查

| 英文 | 中文 | 含义 |
|---|---|---|
| Evaluation | 评测 | 用任务和评分逻辑衡量系统表现 |
| Trial | 试验 | 同一任务的一次独立运行 |
| Trajectory | 执行轨迹 | Agent 的步骤、调用和中间结果 |
| Outcome | 最终状态 | 环境中真实可验证的结果 |
| Grader | 评分器 | 对结果或轨迹进行评分的逻辑 |
| Trace / Span | 轨迹 / 跨度 | 端到端调用链及其中单个操作 |
| Regression Eval | 回归评测 | 防止已有能力退化的评测 |
| Canary Release | 金丝雀发布 | 用小流量逐步验证新版本 |
