## 1. Agent

### 1.1 AI Agent 与普通大模型问答、固定 Workflow 有什么区别？什么场景应该或不应该使用 Agent？

普通大模型问答以理解和生成内容为主，通常只有一次或少量模型调用。RAG（检索增强生成）、Memory（记忆）和 Prompt（提示词）可以增强问答系统，但是否使用这些组件并不是判断 Agent 的标准。

Agent 的核心是围绕目标进行“观察—决策—行动—反馈”的循环：读取当前 State（状态），决定是否调用工具或调整计划，根据执行结果继续推进或结束。固定 Workflow（工作流）的路径主要由代码预先确定，稳定、可预测、成本低且易测试；Agent 的部分路径由模型动态决定，灵活性更高，但也增加延迟、成本、不确定性和安全风险。

当任务需要多步执行、动态选工具、根据中间结果调整路径，且无法穷举全部分支时，适合使用 Agent。流程固定、规则明确、强一致、高风险或强审计场景，应优先使用普通代码或 Workflow。生产系统通常采用混合架构：确定性主流程由代码控制，仅在语义判断和动态决策节点使用模型。

### 1.2 如何避免 ReAct Agent 连续调用相同工具并陷入无限循环？

应同时设置硬限制和进度检测。硬限制包括最大步骤数、模型调用数、工具调用数、总 Token、总费用和总运行时间，任何预算耗尽都必须停止。

对每一步建立调用指纹，至少包含工具名、规范化参数、关键结果和状态版本；检测模型决策、工具调用和状态转换是否重复，不能只比较工具文本。还应定义“有效进展”，例如未完成子目标是否减少、State 是否变化、是否获得新证据。连续多步没有进展，即使模型措辞不同，也应判定为停滞。

触发停滞后，可允许一次重新规划、切换工具或请求用户补充信息；仍无进展则返回部分结果、转人工或失败退出。写操作必须配合幂等机制，避免循环检测生效前已经产生重复副作用。Trace（执行轨迹）中要记录触发条件、停止原因和恢复策略。

### 1.3 创建订单成功但响应丢失，如何避免 Agent 重复创建订单？

这是“执行结果未知”问题，核心是由订单服务提供幂等保证，而不是让模型猜测是否成功。Agent 在第一次业务操作前生成 Idempotency Key（幂等键），将其保存到持久化 State，并在重试和任务恢复时始终复用同一个键。

订单服务以幂等键建立唯一约束，并在事务中保存处理状态、订单编号和结果。相同键再次到达时：已成功则返回原结果；处理中则返回处理中或提供查询接口；确定失败且允许重试时才重新处理。不能只采用“先查询、再创建”，因为并发请求可能同时查到不存在；必须依靠唯一约束、原子写入或等价的并发控制。

如果调用超时，Agent 应先使用原幂等键查询或重试，不能生成新键。幂等记录要有明确的作用域、请求摘要和保留期限，防止同一个键被误用于不同业务请求。

### 1.4 长期任务执行中服务重启，如何利用 State 和 Checkpoint 正确恢复？

State 保存任务当前需要的数据；Checkpoint（检查点）是某个执行边界上的 State 快照和下一步位置；Trace 用于观测与排错，三者不能混为一体。每个节点完成后，应原子地保存节点输出、完成状态、下一节点和状态版本。

重启后，根据任务 ID 读取最新成功 Checkpoint，从其指定的下一节点继续。若某节点在崩溃前标记为运行中，不能无条件重跑：纯计算和只读操作通常可以重试；有副作用的操作必须用原幂等键查询外部系统，确认未执行后才能重试。否则会出现“外部操作已成功，但本地成功状态尚未保存”的重复执行窗口。

多实例恢复时，可在短事务中用数据库锁领取任务，执行期间用 Lease（任务租约）和 Heartbeat（心跳）表示占用，状态更新时用 Version（版本号）防止旧实例覆盖新状态。数据库锁不应跨越长时间的模型或工具调用。

### 1.5 机票和酒店成功、接送车失败，且三个系统不支持统一事务，如何处理部分失败？

首先根据业务语义确定一致性要求：任务是“必须全部成功”，还是允许保留部分成功结果。三个外部系统无法加入同一个本地数据库事务，因此应采用 Saga（分布式补偿事务），为每个正向操作定义对应的补偿操作，并持久化每一步状态。

临时错误，如网络波动、限流和服务暂时不可用，可以使用相同幂等键进行有限次数的指数退避重试；权限不足、参数错误、余额不足等非临时错误不应自动反复重试。如果允许部分成功，就保留机票和酒店并告知用户接送车失败；如果要求全部成功，则通常按相反顺序取消酒店和机票。

补偿不是数据库回滚，取消操作本身也可能失败，因此补偿也要幂等、可重试、可审计。多次失败或状态无法确认时，应暂停流程并转人工处理，同时向用户明确展示当前哪些步骤已成功、失败或待确认。

### 1.6 Agent 变慢且工具经常失败，应该建立哪些可观测信息，如何定位问题？

应建立 Metrics（监控指标）、Trace（执行轨迹）和 Logs（运行日志）三类信号，并通过统一 Trace ID 关联。

- Metrics 用于发现整体异常：成功率、错误率、吞吐量、平均耗时、P95/P99、Token、费用、循环次数和重试次数。
- Trace 用于定位某一次任务卡在哪个节点：每个 Span（执行片段）记录开始时间、耗时、输入输出摘要、状态变化、上下游关系和错误类型。
- Logs 用于解释具体原因：异常堆栈、响应码、超时、数据库或第三方服务错误等。

模型侧关注排队时间、首 Token 时间、总耗时、Token 和重试；RAG 侧拆分查询改写、召回、重排序和上下文组装；工具侧拆分网络、认证、参数校验和业务处理；Agent 侧关注路由、循环、节点等待和状态迁移。排查顺序通常是 Metrics 发现异常范围，Trace 定位异常节点，再用 Logs 查根因。输入输出记录必须脱敏、分级授权并设置保存期限。

### 1.7 Agent 调用模型8次、工具12次、耗时40秒且Token成本高，如何在不明显降低质量的前提下优化？

首先用离线评测和线上 Metrics 建立质量、成功率、延迟和成本基线，再通过 Trace 确认耗时与 Token 主要消耗在哪里，不能凭感觉删除节点。

减少模型调用时，可将确定性路由、格式转换和规则校验下沉到代码；设置明确结束条件；用 Model Routing（模型路由）让简单任务使用小模型，复杂任务再升级；对可合并的简单判断进行批处理。减少工具调用时，可使用 Tool Retrieval（工具检索）、批量接口、只读缓存，并对互不依赖的调用并行执行；设置超时、有限重试和 Circuit Breaker（熔断机制）。

降低 Token 时，应裁剪或摘要历史对话，只保留当前任务需要的结构化 State；控制 RAG 候选数量；压缩工具说明和工具返回；避免每轮重复发送不变内容。缓存键必须包含权限、参数、模型或 Prompt 版本、数据版本和有效期；写操作不能靠缓存代替，应使用幂等机制。

统计和通知等非关键操作可异步执行，但必须先可靠写入任务表、消息队列或 Outbox（事务发件箱）。每项优化都要通过 Ablation Test（消融测试）或 A/B Test（对照实验）验证，确保质量和任务成功率没有显著下降。

### 1.8 什么情况下应该使用单Agent，什么情况下才需要Multi-Agent（多智能体）？多Agent可能带来哪些收益，又会增加哪些成本和风险？

默认应优先使用单Agent，因为它的状态、权限、调试、评测和成本更容易控制。任务即使较长，只要目标统一、上下文共享较多、步骤依赖紧密，通常仍适合使用单Agent配合确定性Workflow。

只有当任务能够拆成职责和输入输出边界清晰的子任务时，才考虑多Agent。例如多个子任务可以真正并行、需要明显不同的专业知识或工具权限、需要隔离上下文，或者需要独立Agent进行生成与复核。

多Agent的收益包括专业化分工、并行执行、上下文与权限隔离、独立扩缩容和交叉验证。代价包括更多模型调用和Token、Agent通信与结果合并成本、共享状态一致性、失败传播、重复工作、安全攻击面以及更高的监控和排错难度。

因此，不能根据“任务复杂”直接决定使用多Agent，而应判断：

子任务是否能够清晰拆分；
是否能够真正并行；
是否需要不同工具、权限或上下文；
多Agent带来的质量或速度收益能否覆盖协调成本。

如果单Agent加Workflow可以稳定完成，就没有必要使用多Agent。

### 1.9 多个Agent并行分析同一个任务，其中两个Agent同时修改共享任务计划，而且给出了冲突的结果。你会如何设计它们之间的通信、共享状态和冲突处理机制，避免互相覆盖或产生不一致结果？

多Agent系统应由独立的 Orchestrator（编排器）负责任务拆分、依赖关系、分发和最终汇总。能够由代码确定的路由和状态处理应使用程序规则，只有需要语义判断的部分才交给模型。

每个子Agent只接收完成当前任务所需的上下文和工具权限。每个子Agent通过结构化消息向编排器提交结果，由编排器统一管理共享状态、处理冲突并按需向其他Agent分发必要信息，子Agent之间不直接传递完整对话。

共享状态应由独立状态存储统一管理。子Agent不能直接覆盖共享数据，只能提交状态变更提案；状态层通过字段所有权、版本号、乐观锁和权限校验决定是否写入。这样可以发现两个Agent基于旧版本同时修改数据的问题。

发生冲突时，优先依据业务规则、数据版本、来源权威性和证据进行确定性处理；需要语义比较时再由仲裁Agent判断；仍无法确定则转人工。最终合并结果必须保留各子结论的来源，方便追踪和复核。

### 1.10 一个多Agent任务中有5个子Agent，其中一个Agent超时，另一个Agent返回的结果置信度很低，但其他3个已经完成。你会如何设计重试、降级、超时控制和最终结果返回机制，避免整个任务一直等待或直接失败？

编排器应为整个任务设置全局 Deadline（截止时间），并为每个子任务设置独立超时、重试次数和成本预算。同时区分关键任务和非关键任务：关键任务失败可能阻止最终结论，非关键任务失败则允许返回部分结果。

子Agent失败后，先进行错误分类。网络超时、限流等临时错误可以使用指数退避进行有限重试；权限、参数和数据缺失问题应修正条件后再执行；低质量结果需要通过规则、证据、结构完整性或独立评审判断，不能只相信Agent自报的置信度。

重试仍失败时，按照预设顺序降级，例如：

切换备用模型或备用Agent；
补充或减少上下文；
使用缓存或最近一次有效结果；
跳过非关键子任务；
返回部分结果并标记缺失内容；
对关键问题转人工处理。

编排器只合并已经通过验证的结果。最终答案应明确区分“已确认结论、待确认结论和缺失结果”，同时在执行详情中展示各子Agent的成功、失败、超时和降级状态，不能为了保证完整而编造失败子任务的内容。

### 1.11 一个Agent需要支持“任务风险分析、敌方趋势预测、我方行动建议”三类输出，每类输出都有不同的Prompt、知识库、分析步骤和工具。你会如何设计路由和加载机制，让每次任务只使用当前需要的能力模块，同时又能处理一个请求同时涉及多类输出的情况？

我会将系统分为任务解析层、能力路由层、能力执行层和结果组装层。

首先，任务解析层从用户请求或上游任务中识别需要的输出类型，并生成可多选的能力列表。然后，能力路由层根据每个能力的输入Schema检查数据是否齐全：用户需要且数据满足时执行；用户需要但数据不足时返回缺失信息；数据齐全但用户没有要求时不自动执行，除非业务规则明确规定必须输出。

每个能力模块独立封装Prompt、RAG知识范围、工具、分析步骤、输出Schema和校验规则。路由完成后，只加载被选中能力的相关内容，避免所有规则和工具同时进入上下文。

多个能力同时触发时，通过DAG描述依赖关系：互不依赖的风险分析和趋势预测可以并行执行；行动建议如果依赖前两者，则等待其完成后再执行。最后由程序根据统一Schema合并结果、去重并处理冲突。

路由还需要设置置信度阈值、缺参处理和默认兜底，并通过多标签分类准确率、漏路由率、误路由率、任务成功率、Token和延迟持续评测。

## 2. RAG

### 2.1 知识库存在正确内容但 RAG 回答错误，如何逐步定位问题？

先保存完整 RAG Trace：原始问题、查询改写、权限与元数据过滤、初始召回、融合结果、重排序结果、最终上下文、完整 Prompt 和模型答案。随后严格按照数据流由前向后排查：

1. **原始文档与解析**：确认正确内容确实存在，解析后是否漏页、乱码、OCR错误或表格错位。
2. **分块与索引**：确认正确内容形成了语义完整的 Chunk，并成功写入正确版本的索引及元数据。
3. **初始召回**：检查正确 Chunk 是否进入候选 Top K；未进入则排查查询改写、Embedding、BM25、过滤条件和索引版本。
4. **融合与重排序**：正确 Chunk 已召回却被融合或 Reranker 淘汰，属于排序问题。
5. **上下文组装**：正确 Chunk 排名足够高却未进入 Prompt，检查去重、Token 预算、截断、顺序和文档冲突处理。
6. **最终生成**：证据完整进入 Prompt 仍回答错误，再检查提示词、模型能力、证据忠实度和引用。

检索阶段使用 Recall@K（前K项召回覆盖率）、MRR（平均倒数排名）或 NDCG（归一化折损累计增益）；生成阶段评估答案正确性、忠实度、引用正确性和拒答准确率。可将正确证据单独提供给模型做对照实验，以隔离检索问题和生成问题。

### 2.2 企业知识库如何设计分块策略？Chunk 过大或过小有什么问题？

分块目标不是追求统一长度，而是在保持语义完整、控制检索粒度和上下文成本之间取得平衡。总体可采用“文档结构优先、语义边界辅助、最大 Token 限制、必要时重叠”的组合策略。

- 制度和技术手册：按章节、标题、段落或操作步骤分块，并把标题路径写入每个 Chunk 的元数据或正文前缀。
- FAQ：一个问题与对应答案组成完整 Chunk。
- 表格：保留表名、表头、行列关系和必要上下文，不能仅抽出孤立单元格。
- 扫描 PDF：先进行版面识别和 OCR，再按标题、段落和页码组织。
- 无结构长文本：按语义或固定长度切分，并设置适度重叠。

Chunk 过大会混入多个主题、稀释向量表示、增加重排序与 Token 成本；过小会破坏证据完整性、增加索引数量，并迫使系统同时召回多个片段才能回答。最终参数应按文档类型，通过召回率、答案质量、延迟和成本评测确定。

### 2.3 为什么企业知识库不能只使用向量检索？如何设计混合检索？

向量检索擅长同义表达、口语化问题和模糊语义，但对设备编号、错误码、文件号、缩写和罕见专有词可能不稳定。BM25（关键词相关性排序）擅长词面精确匹配，但难以处理同义改写和用词不一致。因此两者是互补关系，而不是按“某类知识库只能选一种”进行静态划分。

生产中通常让 BM25 与向量检索并行召回，经过去重后使用 RRF（倒数排名融合）或经过校准的加权融合，再使用 Reranker（重排序模型）进行细粒度排序。可根据查询特征动态调整权重，例如检测到编号或错误码时提高关键词检索权重，但仍保留另一条召回通道作为补充。

参数不能只看最终答案，应同时使用 Recall@K、排序指标、答案正确率、延迟和成本评测。

### 2.4 为什么不能直接选择向量相似度最高的5个片段？Reranker解决什么问题？

向量相似度表示的是粗粒度语义接近，不等于片段能够直接回答问题。混合检索中 BM25 分数和向量分数的尺度也不同，不能直接只按某一路的分数截取结果。初始召回的目标是保证覆盖率，重排序的目标是在候选集中提高前几名的精度。

Reranker 通常同时读取问题和候选片段，判断细粒度相关性或答案支持程度，再结合文档权威性、版本、新鲜度和业务规则排序。它会增加推理延迟、计算资源和成本，也可能因领域不匹配、长文本截断或排序错误把正确证据降权。

Reranker 只能重新排列已召回的候选，不能找回初始召回遗漏的证据。因此应分别评估候选召回覆盖率和重排序后的 Top K 质量。

### 2.5 如何构建评测集并证明 RAG 准确率从60%提升到85%？

优先从真实历史问题、用户反馈、线上失败案例和业务专家整理的问题中取样；模型生成的问题只能用于补充覆盖，必须经过人工审核。每道题应保存问题类型、标准答案、支持证据、可接受答案范围、文档版本和是否应拒答。

评测集要覆盖语义查询、编号与专业术语、多跳与多文档、表格、版本冲突、无答案、权限隔离、对抗问题和长上下文问题。数据划分为 Development Set（开发集）和独立 Test Set（测试集）：开发集用于调参，测试集在方案冻结后才用于最终比较，避免测试集泄漏和针对性刷分。

应分别评估检索覆盖率、排序质量、答案正确性、证据忠实度、引用正确性、拒答准确率、延迟和成本；既按真实流量加权报告总体结果，也要报告各类问题切片。新旧系统必须在相同数据、模型版本和运行条件下比较，并报告样本量、置信区间或显著性，结合盲审和线上小流量 A/B Test，才能说明提升可信，而不是只报一个总体百分比。

### 2.6 知识库没有答案时，如何识别“无法回答”并减少幻觉？

首先在召回和重排序阶段过滤明显不相关的内容，但相关性高不等于证据足以回答。系统还需要进行 Answerability（可回答性）或 Evidence Sufficiency（证据充分性）判断：结构化问题可用必填字段和规则判断，自由文本可用专门分类器、NLI（自然语言推断）模型或受约束的大模型判断证据是否完整支持答案。

证据不足时，应直接返回“知识库暂无足够信息”，说明缺少什么，并允许用户补充条件或转人工。生成阶段要求模型只依据证据回答、为关键结论提供引用；生成后再进行 Claim Verification（结论验证），检查每个关键结论是否被引用片段支持，无法支持的内容删除、降级为不确定表述或整体拒答。

阈值必须使用同时包含可回答和不可回答问题的评测集校准。Prompt 约束是辅助措施，不能作为唯一防幻觉机制；权限过滤必须在检索前完成。

### 2.7 企业 RAG 如何实现文档权限控制？为什么不能先召回再隐藏？

身份认证后，服务端从权限系统获得用户、租户、部门、角色、用户组和资源授权。文档解析与分块时，为每个 Chunk 写入租户、文档、访问控制列表、版本和敏感级别等元数据。查询时由服务端生成不可被模型修改的过滤条件，在向量和关键词检索阶段就完成权限过滤。

不同租户或高度敏感数据可采用独立索引、集合或数据库实现物理隔离；租户内部共享可使用统一索引加元数据过滤。权限变更、文档撤权和删除必须同步更新索引与权限缓存，并记录访问审计。

先召回再隐藏会让无权限内容占据 Top K，降低有效召回率并浪费重排序和 Token；更严重的是，无权限内容已经进入缓存、日志、Trace、应用内存或模型上下文，构成实际泄露。权限控制必须由服务端强制执行，不能依赖 Prompt 或模型自觉。

## 3. Memory

### 3.1 如何区分短期记忆和长期记忆，并设计长期记忆的写入、检索、更新与删除？

短期记忆是线程或任务范围内的工作状态，包括近期对话、当前计划、工具结果和 Checkpoint；长期记忆是跨会话仍有价值的信息，例如用户确认的稳定偏好、长期约束和重要事实。长期不等于永久，仍需有效期、更新和删除机制。

写入长期记忆前应判断未来价值、稳定性、来源可靠性、用户确认状态和敏感程度。明确要求记住且合规的信息可以保存；模型从单次对话推断出的偏好不能直接当成事实，应提高确认门槛。密码、验证码、访问令牌等凭证不能写入普通 Memory。

检索时按用户、租户和任务范围过滤，再综合语义相关性、重要性、新鲜度和置信度召回少量内容。更新时处理冲突、保留来源与版本，不应简单追加矛盾事实。删除要支持用户主动删除、自动过期和合规删除，并同步清理主数据库、向量索引、缓存和派生副本。

### 3.2 如何防止恶意或越权信息污染长期记忆？

记忆写入应采用 Schema Allowlist（结构类型白名单），只允许保存预先定义的偏好、事实和项目约束。网页、邮件、知识库和工具结果默认是不可信数据，没有修改系统规则、权限或记忆的指令权。

每条记忆都应记录所属用户与租户、来源、时间、置信度、确认状态和版本。修改他人记忆、取消审批、扩大权限、覆盖系统规则等内容，即使用户要求记住，也不能直接生效；权限只能由独立的授权系统和管理员流程修改。API Key、密码和验证码应进入密钥管理系统，而不是长期记忆。

使用记忆时仍要重新进行权限和策略校验，不能因为某条记忆写着“无需审批”就绕过工具安全。系统还应支持审计、冲突检测、回滚、删除和异常写入告警。

## 4. MCP 与 Function Calling

### 4.1 MCP 与 Function Calling 有什么区别？何时使用本地工具，何时使用 MCP？

Function Calling（函数调用）是模型表达工具调用意图的结构化机制：应用向模型提供工具名称、描述和 JSON Schema（参数结构），模型返回工具名与参数，应用负责校验、授权和实际执行。它不是工具实现，也不自动执行函数。

MCP（模型上下文协议）是 AI 应用连接外部系统的标准协议，规范客户端与服务端如何发现和访问 Tools（工具）、Resources（资源）和 Prompts（提示模板）等能力。MCP Server 可以在本地或远程运行，因此 MCP 不等于互联网工具。

两者可以组合：MCP 负责标准化提供和调用工具，Function Calling 负责让模型结构化表达“选哪个工具、传什么参数”。固定 Workflow 也可以不经过模型，直接调用 MCP 工具，所以 MCP 并不强制要求 Function Calling。

工具少、只服务单项目、与业务代码紧耦合且追求最低延迟时，本地工具更简单；工具需跨应用、跨语言、跨进程或跨团队复用，或需要动态发现和独立维护时，更适合 MCP。是否使用 MCP 不改变权限校验、审批和审计责任。

### 4.2 上千个工具如何进行 Tool Retrieval，避免漏召回和功能重叠？

先为工具建立规范元数据：名称、功能、输入输出、适用与禁止场景、权限、风险等级、环境、资源类型、版本和示例。检索前先按用户权限、租户、环境和风险策略做确定性过滤，再进行分层或全局候选召回。

可先通过规则、轻量模型或分类器选择多个相关领域，再在这些领域中使用关键词与向量混合检索，最后用 Reranker 排序，只把少量工具定义交给主模型。分类必须支持多选；置信度低、候选工具无法满足参数要求或执行失败时，应触发全局检索兜底，而不是逐个分类盲目重试。

功能重叠不能仅靠把工具分到不同分类解决。应合并重复工具、设置权威版本和优先级，并在描述中明确差异、前置条件和禁止场景；再根据权限、环境、资源归属和参数完整性过滤。仍无法唯一判断时，应向用户澄清。离线评测重点关注 Tool Recall@K（正确工具召回率）、Top-1 选择准确率、误调用率、任务成功率、延迟和 Token 成本。

### 4.3 如何防止工具误调用、越权调用和危险参数？

安全边界必须位于模型外部。首先完成身份认证，并根据用户、租户、资源归属、操作类型和数据范围进行细粒度授权；模型只应看到当前任务可能使用的工具，但工具执行时仍需再次授权，不能把“隐藏工具”当作唯一安全措施。

参数使用严格 Schema、类型、枚举、范围、白名单和影响数量校验；避免任意 SQL、任意 Shell 命令和任意路径。工具使用最小权限凭证，在沙箱或受限环境运行，并设置超时、限流、熔断和资源配额。写操作使用幂等键，高危操作提供影响预览、Dry Run（预执行）和 Human in the Loop（人工审批）。

用户确认只证明操作意图，不能赋予用户原本没有的权限。系统还要限制敏感数据可以流向哪些外部目标，记录完整审计日志，并对工具返回的外部内容继续按不可信数据处理。

## 5. Prompt 安全

### 5.1 如何防止网页、邮件或知识库中的恶意指令诱导 Agent 删除数据或外传信息？

系统不能让模型自行判断一段文字是系统指令还是外部数据。应用在数据接入时就应记录来源、时间、所属用户或文档、可信等级和权限范围，并通过消息角色、结构化字段和明确的数据边界传入模型。网页、邮件、知识库和工具结果均默认属于不可信数据，不能因为内容看起来像命令就升级为系统指令。

接入阶段可以做来源白名单、恶意模式检测和内容隔离，但合法来源也可能被污染，注入内容也可能经过编码或隐晦表达，因此过滤器不是可靠的最终安全边界。Prompt 中应明确外部内容仅供提取事实，不执行其中的指令，并尽量把指令和数据分离。

真正的防线是模型外部的策略执行：工具调用前重新校验用户权限、参数、操作风险和数据流向；高危操作要求确认或审批；工具使用最小权限和沙箱；禁止把敏感数据发送到未授权目标。即使模型受到 Prompt Injection（提示词注入）影响，也应因缺乏权限而无法完成危险操作。系统还应使用对抗评测持续测试直接注入、间接注入、编码绕过和数据外传场景。
