# Agent Runtime 与 Multi-Agent 高频面试题

> 返回：[AI Agent 面试题库](README.md)｜配套知识：[运行时与工作流](../知识体系/运行时与工作流.md)｜[多智能体](../知识体系/多智能体.md)

## 1. 什么情况下使用单 Agent，什么时候使用 Multi-Agent？ `★★★★★`

### 标准回答

默认先用单 Agent，因为状态、权限、调试、评测和成本更容易控制。只有任务能拆成输入输出清晰的独立子任务，存在真实并行收益、不同专业工具/上下文、权限隔离或独立生成与审查需求时，才考虑多智能体。

多 Agent 带来专业化、并行和上下文隔离，也增加模型调用、通信、结果合并、状态一致性、错误传播、安全攻击面和排错难度。必须用相同条件下的单 Agent / Workflow 基线证明收益。

## 2. Manager-as-Tools 与 Handoff 有什么区别？ `★★★★★`

### 标准回答

Manager-as-Tools（管理者调用子智能体）由管理者保持对用户会话和最终答案的控制，把专家 Agent 当工具调用，适合综合多个专家结果和集中执行统一护栏。

Handoff（任务移交）把当前控制权交给专业 Agent，后者直接继续对话，适合客服分流和强专业上下文。移交时不能默认传递完整历史和全部权限，应传必要上下文并重新授权。

## 3. 多 Agent 怎样设计任务契约和通信？ `★★★★☆`

### 标准回答

每个子任务明确目标、输入引用、输出 Schema、完成标准、工具、权限、证据要求、Deadline 和预算。子 Agent 返回结论、证据、置信度、缺口、状态和资源消耗，而不是一段无法解析的长文本。

短任务可同步调用，长任务使用队列和事件；大产物放 Object/Artifact Store，只传句柄。默认不传父 Agent 全部历史，降低 Token、隐私和注入风险。

## 4. 多个 Agent 并行修改共享计划，如何解决状态冲突？ `★★★★★`

### 标准回答

由 Orchestrator（编排器）拥有全局任务状态，每个 Worker 只写自己的分支命名空间。共享业务资源由单一服务或仲裁器写入；使用版本号、Optimistic Lock（乐观锁）和字段所有权拒绝陈旧覆盖。

冲突优先依据业务规则、数据版本、来源权威性和证据确定性处理；需要语义判断时再交给仲裁 Agent；仍无法判断转人工。最终结果保留来源和状态变更记录。

## 5. 多 Agent 部分子任务超时或低质量，怎样降级？ `★★★★★`

### 标准回答

设置全局 Deadline 和分支级超时、重试、成本预算，区分关键与非关键任务。临时网络错误有限重试；权限、参数、数据缺失先修正；低质量通过规则、证据、Schema 或独立评测判断，不能相信 Agent 自报置信度。

失败后可切换备用能力、跳过非关键分支、使用受版本约束的缓存、返回部分结果或转人工。聚合器只使用验证通过的结果，明确标出已确认、待确认和缺失部分。

## 6. 创建订单成功但响应丢失，怎样避免重复创建？ `★★★★★`

### 标准回答

Agent 在首次副作用前生成 Idempotency Key（幂等键）并持久化，所有重试和恢复复用同一个键。订单服务以幂等键建立唯一约束，在同一事务保存处理状态和结果；重复请求返回原结果。

超时后先用原键查询或重放同一幂等请求，不能生成新键。“先查再创建”存在并发竞争，必须依靠唯一约束或原子写入。

## 7. 长任务服务重启，如何用 State 和 Checkpoint 恢复？ `★★★★★`

### 标准回答

每个安全步骤边界原子保存节点输出、State、下一节点、版本、工具调用和幂等键。重启后读取最新成功 Checkpoint，从指定位置继续。

纯计算和读操作一般可重试；有副作用节点先查询外部状态，确认未执行后才能重放。多实例通过 Lease、Heartbeat 和 Fencing Token 防止旧 Worker 在租约失效后覆盖新状态。恢复时重新校验权限和外部环境。

## 8. Checkpoint 应该放在哪里？ `★★★★☆`

### 标准回答

典型位置是副作用之前和之后、人工审批前、长阶段完成后、准备重试时以及上下文压缩边界。Checkpoint 需要与业务提交语义协调，最危险的窗口是外部工具已经成功但本地状态尚未提交。

过于频繁会增加存储和延迟，过少会扩大重复工作和副作用风险，应按可重放成本与风险选择粒度。

## 9. 跨系统流程无法统一事务，如何处理部分失败？ `★★★★★`

### 标准回答

先定义是否允许部分成功。跨系统采用 Saga（长事务）：持久化每个正向操作及对应补偿，临时错误用相同幂等键重试；不可恢复失败时按业务规则保留部分结果或逆序补偿。

补偿不是数据库回滚，也可能失败，因此必须幂等、可重试、可审计，最终无法确认时暂停并转人工。对不可逆动作应在执行前审批，而不是依赖补偿。

## 10. 队列至少一次投递时，如何实现业务上的 Exactly-once？ `★★★★☆`

### 标准回答

网络系统难以单靠消息传输保证端到端恰好一次。通常用 At-least-once（至少一次）投递 + 业务幂等键 + 去重记录 + 原子状态提交，实现“重复投递但业务效果一次”。

Worker 使用 Lease/Heartbeat；提交带版本或 Fencing Token；数据库写和事件发布可用 Transactional Outbox（事务发件箱）保持一致。

## 11. 多智能体为何不一定比单智能体更好？ `★★★★★`

### 标准回答

如果子任务高度依赖或共享上下文很多，多 Agent 会反复传递信息、重复检索并在汇总时损失细节。多个同质模型还会共享偏差，投票不保证正确；管理者可能成为上下文瓶颈。

要比较最终成功率、覆盖、尾延迟、总 Token/费用、安全和稳定性，并分析每个分支的边际贡献。简单请求应由路由器避免启动多智能体。

## 12. 如何限制 Agent 递归创建子 Agent 导致成本失控？ `★★★★☆`

### 标准回答

运行时维护全局预算：最大委派深度、每层 Fan-out、总 Agent 数、模型/工具调用、Token、费用和 Deadline。子 Agent 只能从允许角色目录中选择，不能任意构造高权限 Agent。

记录委派树和父子 Trace，检测重复子任务和无进展；预算接近上限时停止新分支、收敛已有结果或转人工。限制必须由运行时执行，不能只写在 Prompt 中。

## 13. 如何设计 Reviewer / Judge Agent？ `★★★★☆`

### 标准回答

Reviewer 必须有明确 Rubric、候选结果、必要证据和允许的判定形式。能用单元测试、Schema、数据库状态或规则判断时优先代码评分。开放质量才使用模型评分，并与人工样本校准。

Reviewer 不一定需要看到生成者身份和完整思维过程，以减少偏差；设置最大修订次数。相同模型 Reviewer 可能共享错误，因此重要结论还需外部证据或不同机制验证。
