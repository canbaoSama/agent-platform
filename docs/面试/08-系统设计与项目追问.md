# Agent 系统设计与项目追问

> 返回：[AI Agent 面试题库](README.md)｜配套知识：[AI Agent 知识体系](../知识体系/README.md)

开放题没有唯一架构，但存在明确评价标准：需求澄清、边界合理、数据流完整、可靠安全、指标可验证，并能说明取舍。

## 1. 设计一个企业知识问答 Agent。 `★★★★★`

### 标准回答

先确认用户规模、知识类型、更新频率、权限、延迟和错误成本。主链路：认证 → 意图/风险分类 → 租户与 ACL 过滤 → 查询改写 → BM25 + 向量召回 → 融合与重排 → 证据充分性 → 上下文组装 → 生成与引用核验 → 拒答或返回。

离线侧处理解析、结构化分块、元数据、Embedding、版本索引和原子发布。权限必须在检索阶段执行。评测包含 Recall@K、答案正确性、忠实度、引用、拒答、P95 和成本；保存 Trace 定位解析、召回、重排和生成问题。复杂跨源任务才进入 Agentic RAG，普通查询走低成本固定链路。

## 2. 设计一个能查询订单并执行退款的客服 Agent。 `★★★★★`

### 标准回答

外层使用确定性状态机：身份验证、订单归属、退款资格和金额限制由业务服务决定；LLM 负责理解意图、收集缺失信息、选择允许的查询工具和生成解释。

退款工具执行前按真实主体和订单重新授权，高金额进入人工审批；写操作使用幂等键，副作用前后保存 Checkpoint；超时后先查状态再重试。RAG 提供政策但不能代替真实订单状态和权限。最终 Outcome 由支付/订单系统验证，并记录审计、Trace、拒绝原因和人工接管。

## 3. 设计一个支持上千工具的 Agent 平台。 `★★★★★`

### 标准回答

建立 Capability Registry（能力注册中心），保存工具名称、版本、Schema、领域、权限、风险、环境和健康状态。请求先经过认证和策略过滤，再做领域分类、关键词/向量工具检索与重排，只把少量候选 Schema 交给模型。

统一执行网关负责参数校验、授权、凭证注入、限流、超时、幂等、审计和结果规范化。高风险工具审批和沙箱；工具版本灰度与回滚。指标分为候选 Recall@K、选择/参数准确率、执行成功、任务 Outcome、延迟和成本。

## 4. 设计一个跨小时运行、可暂停审批的 Deep Research Agent。 `★★★★★`

### 标准回答

使用持久化 Orchestrator + Queue + Worker。高层计划拆成带输出 Schema、来源和预算的子任务，可独立方向并行；每个阶段输出保存到 Artifact Store，并在步骤和副作用边界保存 Checkpoint。

等待审批时持久化状态并释放 Worker；恢复时重验权限与外部状态。全局限制深度、扇出、Token、费用和 Deadline；分支支持超时、重试、取消、最低完成数和部分结果。最终聚合做去重、冲突和引用核验，并保留父子 Trace。

## 5. 如何估算 Agent 系统容量和成本？ `★★★★☆`

### 标准回答

从业务流量而不是单次模型调用估算：QPS、并发、平均/峰值轮数、每轮输入输出 Token、RAG/工具次数、重试率、并行分支、模型价格和缓存命中。并发近似可由到达率 × 平均服务时间估算，再为 P95、突发和依赖限流留余量。

分别估算模型、向量检索、Reranker、工具、队列、存储和 Trace 成本。关键指标是 Cost per Successful Task（每个成功任务成本）。容量测试要包含长上下文、慢工具、重试和多 Agent 峰值，而非只压测一个健康检查接口。

## 6. 线上 Agent 成本突然上涨 3 倍，如何排查？ `★★★★★`

### 标准回答

先按模型/Prompt/租户/任务类型切分单任务 Token、轮数、工具次数、重试和并行宽度，确认从何时和哪个版本开始变化。沿 Trace 检查历史是否无限增长、工具返回是否变大、路由是否误用强模型、循环是否增加、缓存是否失效、下游超时是否触发重试风暴。

修复后不仅看总费用，还验证任务成功率和延迟没有退化，并增加预算告警、循环检测、版本对比和回归用例。

## 7. 离线评测变好，但线上用户反馈变差，可能是什么原因？ `★★★★★`

### 标准回答

可能是评测分布与真实流量不一致、数据泄漏、评分器偏差、线上工具/权限/延迟未被模拟、Prompt 或知识版本不同、失败重试和长会话未覆盖，或优化了平均分却损害某个高价值切片。

核对线上版本和 Trace，按用户类型、任务、语言和风险切片；抽样人工阅读轨迹与 Outcome；把线上失败转成回归任务。离线评测、生产监控、A/B、用户反馈和人工审查要结合，不能用一个分数替代全部事实。

## 8. 更换更强模型后效果反而下降，如何解释和处理？ `★★★★☆`

### 标准回答

模型能力更强不代表与现有 Harness（运行框架）更匹配。它可能更倾向调用工具、输出格式不同、对 Prompt 优先级理解不同、Token 与延迟更高，或与旧路由、停止条件和评分器发生不兼容。

锁定相同数据与环境，比较工具选择、参数、轨迹长度、RAG 使用、拒答和 Outcome；按失败切片调整 Prompt、工具描述与运行时，而不是盲目回退或宣布新模型更差。通过 Canary 发布并保留快速回滚。

## 9. Python 中如何并发执行多个独立 I/O 工具？ `★★★★☆`

### 标准回答

网络、数据库等 I/O-bound（I/O 密集）任务通常使用 `asyncio` 并发，统一设置超时、取消和并发 Semaphore（信号量）。阻塞库可放线程池；CPU-bound（计算密集）任务使用多进程、原生扩展或独立计算服务，避免阻塞事件循环。

并发不是无上限 `gather`：要考虑下游限流、连接池、背压、全局 Deadline、部分失败和结果顺序。写工具还要处理幂等与共享状态冲突。

## 10. 如何设计 Agent 的缓存？ `★★★★☆`

### 标准回答

可缓存 Prompt 前缀、Embedding、只读工具结果、检索候选和确定性中间产物。缓存键至少包含租户/权限、规范化参数、模型/Prompt/工具/知识版本和数据版本；设置 TTL、大小限制和失效机制。

语义缓存只能用于允许近似复用的低风险答案，需阈值和结果验证。写操作不能用缓存替代幂等。缓存命中也要记录来源与版本，防止跨租户泄露和过期事实。

## 11. “介绍你做过最复杂的 Agent 项目”，怎样回答？ `★★★★★`

### 标准回答框架

1. 场景：用户是谁，原流程痛点和错误成本是什么。
2. 目标：成功率、延迟、成本或人工效率的基线和目标。
3. 架构：为何用 Agent，哪些步骤仍由 Workflow；Context、RAG、Memory、Tool 和 Runtime 怎样连接。
4. 难点：挑一个真实 Bad Case，说明如何通过 Trace 和对照实验定位。
5. 取舍：为何没选更复杂方案，安全与可靠性怎样保证。
6. 结果：给出定义明确的指标、实验条件和个人贡献。
7. 复盘：当前局限和下一步。

不要只列 LangChain、向量库等组件；面试官通常会追问为何这样设计、失败时怎样恢复、指标如何计算。

## 12. 如何证明某项 Agent 优化是你个人的贡献？ `★★★★☆`

### 标准回答

明确自己拥有的问题和决策，例如建立某套评测、设计工具检索、修复幂等窗口或推进灰度发布。说明你提出的假设、完成的实验、与他人协作边界、最终代码/设计/指标及复盘。

量化结果要说明口径和对照：在哪个数据集、版本、时间窗口下，成功率、P95 或单成功任务成本如何变化。不能把团队总结果全部归给自己，也不要虚构绝对数字。

## 13. 面试官追问“你的方案最大缺点是什么”，怎样回答？ `★★★★★`

### 标准回答

指出真实且与方案相关的限制，并说明为何当时接受、怎样监控、何时触发演进。例如共享索引降低成本但提高隔离复杂度，因此检索前强制租户过滤并设置泄露回归；单 Agent 简化状态，但广度研究速度不足，达到特定任务比例后再评估并行子 Agent。

好的回答体现 Trade-off（取舍），而不是说“没有缺点”，也不是给出与岗位无关的性格套话。

## 14. 如何回答“如果重做一次，你会改什么”？ `★★★★☆`

### 标准回答

选择一个基于真实证据的改进：例如更早建立 Outcome 评测、更早划分状态所有权、将权限从 Prompt 移到执行网关、先做单 Agent 基线再引入多 Agent。说明当时信息为什么不足、后来出现了什么证据、改动能避免什么成本。

重点不是否定原项目，而是展示从故障和数据中学习并更新架构的能力。
