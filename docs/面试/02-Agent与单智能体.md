# Agent 与单智能体高频面试题

> 返回：[AI Agent 面试题库](README.md)｜配套知识：[Agent 与单智能体](../知识体系/Agent与单智能体.md)

## 1. AI Agent、普通大模型问答和固定 Workflow 有什么区别？ `★★★★★`

### 标准回答

普通大模型问答主要完成理解和生成，通常只有一次或少量模型调用。Agent 的核心是围绕目标执行“观察—决策—行动—反馈”循环：读取 State（状态），决定下一步是否调用工具或调整计划，再根据 Observation（观察结果）继续或结束。

Workflow（工作流）的路径主要由代码预先确定，稳定、可预测、成本低且易测试；Agent 的部分路径由模型动态决定，灵活性更高，但也增加不确定性、延迟、成本和安全风险。RAG、Memory 和 Prompt 都可能出现在问答或 Agent 中，不是判定 Agent 的充分条件。

任务需要多步执行、动态选择工具、根据中间结果改变路径且无法穷举分支时适合 Agent。路径固定、强一致或高风险场景优先使用代码或 Workflow。生产中常采用确定性外壳 + Agentic Node（智能体节点）的混合架构。

## 2. ReAct 是什么？与 Plan-and-Execute 有什么区别？ `★★★★★`

### 标准回答

ReAct（推理与行动协同）把推理、工具行动和环境观察交错进行，适合环境不确定、需要边做边获取信息的任务。Plan-and-Execute（先规划后执行）先生成较完整计划，再由执行器逐步执行，便于审查、并行和进度管理，但初始计划可能随着新信息过时。

长任务通常采用混合方案：先生成高层里程碑，每一步再根据最新 Observation 选择具体动作，并允许有限次数 Replanning（重规划）。无论使用哪种模式，都要有显式 State、预算、终止条件和工具错误处理，不能把自然语言计划当可靠状态机。

## 3. 一个 Agent 需要按需使用不同 Prompt、知识库和工具，如何设计能力路由？ `★★★★★`

### 标准回答

我会分为任务解析、规则筛选、候选能力检索、模型选择和执行校验五层。

首先由确定性规则根据用户、租户、环境、权限和风险过滤不允许的能力。然后识别意图和所需输出，可用分类器、关键词或 Embedding（嵌入）从能力目录召回候选。主模型只看到少量候选能力的 Prompt、RAG 范围、工具和输出 Schema，并在其中选择。真正执行前按具体参数再次授权。

每个能力模块独立封装适用条件、输入输出、工具、知识范围、版本和评测集。多个能力可用 DAG 表达依赖：无依赖的并行，有依赖的等待。需要监控正确能力 Recall@K、Top-1 准确率、误路由、漏路由、任务成功率、Token 与延迟。

## 4. Agent 的 State、Context、Memory 和 Trace 有什么区别？ `★★★★★`

### 标准回答

- State（状态）：当前任务进行到哪里，例如已完成步骤、订单 ID 和剩余预算。
- Context（上下文）：某一次模型调用实际看到的全部内容。
- Memory（记忆）：值得跨轮次或跨任务复用的信息，如稳定偏好和经验。
- Trace（执行轨迹）：系统如何走到当前状态，包括模型、工具、路由和耗时。

State 是业务和控制真相，Context 是当次推理输入，Memory 服务未来复用，Trace 服务调试和审计。它们可以使用相同数据库，但生命周期、写入者和一致性要求不同。

## 5. 如何为 Agent 设计终止条件？ `★★★★★`

### 标准回答

完整终止机制包含：

1. 可验证成功条件，例如数据库中确实存在目标记录，而不是模型说“完成”。
2. 不可恢复失败条件，例如授权拒绝或必需数据不存在。
3. 步数、时间、Token、费用和工具次数预算。
4. No-progress Detection（无进展检测），识别重复动作和状态不变。
5. 高风险或无法判断时转人工。
6. 预算耗尽时返回已完成部分、缺口和继续方式。

只设置 `max_steps` 能阻止无限运行，但无法判断是否真的完成，也无法避免预算耗尽前产生重复副作用。

## 6. 如何避免 ReAct Agent 连续调用相同工具并陷入循环？ `★★★★★`

### 标准回答

硬限制包括最大步骤、模型调用、工具调用、Token、费用和总 Deadline。软检测要对每步建立调用指纹，包含工具名、规范化参数、关键结果和 State 版本；同时判断未完成子目标是否减少、是否获得新证据或状态是否变化。

连续多步没有进展时，允许一次重规划、切换工具或向用户补充询问；仍无进展就降级、返回部分结果或失败退出。写操作必须具备幂等键，防止循环被发现前已造成重复副作用。Trace 中记录停止原因和重复模式，加入离线回归集。

## 7. Agent 为什么需要 Structured Output？是否能完全相信它？ `★★★★☆`

### 标准回答

Structured Output（结构化输出）让计划、路由、工具参数和最终结果遵守 Schema，便于程序校验、分支和持久化，比解析自然语言稳定。

但它只解决结构正确性。`amount=1000000` 可能类型合法却违反业务限制，工具名合法也可能不在当前用户权限内。因此还要进行语义、权限、额度、资源存在性和风险校验。模型输出永远是候选决策，不是授权凭证。

## 8. Reflection（反思）或 Critic Agent 一定能提升质量吗？ `★★★★☆`

### 标准回答

不一定。反思可在存在清晰验证标准时发现遗漏，例如代码测试失败、引用缺失或 Schema 不完整；但也会增加调用、延迟和成本，并可能把原本正确的答案改错。相同模型的 Critic 还可能共享生成者的偏差。

优先使用代码测试、数据库状态和规则等确定性验证。只有开放质量无法程序化判断时才用模型评分，并提供明确 Rubric（评分准则）、证据和最大迭代次数。最终是否保留反思环节要通过消融评测证明。

## 9. Agent 调用模型和工具过多，如何优化成本和延迟？ `★★★★★`

### 标准回答

先用 Trace 确认成本在模型、RAG、工具、重试还是排队，建立任务成功率、P95 延迟和单成功任务成本基线。

- 将确定性路由、格式转换和规则校验下沉到代码。
- 用 Model Routing（模型路由）让简单步骤使用小模型，困难任务再升级。
- 做 Tool Retrieval，只加载相关工具；合并批量接口，并行无依赖读操作。
- 裁剪历史，保留结构化 State；压缩 RAG 和工具结果。
- 设置明确终止、有限重试和缓存版本键。
- 将非关键通知异步化，但先可靠写入队列或 Outbox（事务发件箱）。

每项优化都要做 Ablation Test（消融测试）或 A/B Test，防止以质量下降换取表面成本降低。

## 10. 怎样测试一个非确定性的 Agent？ `★★★★★`

### 标准回答

分层测试：

- 代码层测试路由、权限、状态机、幂等和重试。
- 使用 Scripted Model（脚本化模型）模拟工具调用与错误，确定性测试编排器。
- 组件层评估工具选择、参数、RAG、Memory 和 Guardrail。
- 端到端运行多个 Trial（试验），验证真实 Outcome、允许的轨迹范围、成本和安全约束。
- 开放文本用清晰 Rubric 的模型评分器并与人工校准。

不能只断言最终字符串相等，也不能只看模型最终自述；多个路径可能都正确，错误路径也可能碰巧给出正确文字。

## 11. 怎样设计 Agent 的 Prompt？ `★★★★☆`

### 标准回答

Prompt 应明确角色、目标、边界、可用能力、输出格式、证据要求和停止条件，并给出少量高价值示例。工具描述重点说明何时使用、何时不使用和关键参数，而不是重复实现细节。

不要把动态知识、几十条权限规则和全部历史永久堆在 System Prompt 中。动态事实来自 RAG/工具，硬权限由策略引擎执行，历史由上下文工程筛选。Prompt 修改要版本化并通过回归评测，而不是依赖人工试几条。

## 12. 什么情况下不应该使用 Agent？ `★★★★★`

### 标准回答

规则可穷举、流程稳定、延迟极低、要求强一致、无法容忍概率决策或没有可靠安全边界时，不应默认使用 Agent。简单分类、固定数据转换和数据库 CRUD 往往用普通代码更合适。

判断标准不是任务听起来“智能”，而是 Agent 是否在业务评测上相对规则或 Workflow 带来可衡量收益，并且收益覆盖成本、风险和维护复杂度。
