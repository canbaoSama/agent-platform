# Context Engineering 与 Memory 高频面试题

> 返回：[AI Agent 面试题库](README.md)｜配套知识：[上下文工程](../知识体系/上下文工程.md)｜[Memory](../知识体系/Memory.md)

## 1. Prompt Engineering 与 Context Engineering 有什么区别？ `★★★★★`

### 标准回答

Prompt Engineering（提示词工程）关注指令怎样表达；Context Engineering（上下文工程）关注某一步推理时模型实际看到哪些信息。Context 包括系统指令、用户输入、历史、State、工具定义和结果、RAG 证据、Memory、身份权限、预算和输出契约。

生产优化不只是改 Prompt，而是选择、排序、压缩、隔离和更新上下文。目标是最小且充分的高信号信息，而不是把窗口塞满。

## 2. 一个生产级 Agent 的上下文怎样组装？ `★★★★★`

### 标准回答

先由身份和策略层确定允许的能力；加入当前目标、不可变约束、结构化 State 和必要的近期消息；再按需召回 RAG、Memory 和相关工具定义；随后去重、解决冲突、按价值排序并控制 Token Budget；最后明确区分可信指令和不可信外部数据。

每条内容记录来源、版本、权限、时间和入选/过滤原因，使“为什么没看到某条信息”可以通过 Trace 定位。

## 3. 长上下文窗口能否替代 RAG 和 Memory？ `★★★★★`

### 标准回答

不能一概替代。长上下文适合一次性小规模材料和需要全局阅读的任务；RAG 适合大规模、频繁更新、需权限过滤和引用的知识；Memory 负责跨会话复用有价值的信息。

窗口增大仍有成本、延迟、噪声和 Lost in the Middle（中间信息利用较弱）问题，也不能自动解决数据更新、删除和授权。实际系统通常组合使用，并按当前步骤即时加载。

## 4. 上下文很长时如何压缩，避免丢失重要信息？ `★★★★★`

### 标准回答

使用“近期原文 + 结构化 State + 历史摘要 + 按需检索”的混合方式。压缩内容应包含目标、不可变约束、已确认决定、完成步骤、证据引用、失败尝试、未完成事项和下一步。

摘要不是事实真相，要保存来源消息 ID 和版本，关键内容可回查原文。不要在旧摘要上无限递归摘要，否则错误会累积；应定期从原始证据重新生成并做一致性检查。

## 5. Context Pollution 与 Context Rot 是什么？ `★★★★☆`

### 标准回答

Context Pollution（上下文污染）是无关、错误、过期或恶意内容进入输入并干扰模型；Context Rot（上下文退化）是长任务中关键约束逐渐稀释、旧错误反复被摘要、信息利用率下降。

治理包括来源配额、相关性与时效过滤、去重、结构化 State、渐进式加载、工具结果裁剪、重新压缩和关键指令回归测试。

## 6. 如何区分短期记忆和长期记忆？ `★★★★★`

### 标准回答

短期记忆服务当前会话或任务，例如近期消息、当前计划和临时工具结果；长期记忆跨会话仍有价值，例如用户确认的稳定偏好、重要事实和被验证的经验。

按功能还可分 Semantic（语义事实）、Episodic（情景事件）、Procedural（程序经验）和 Preference（偏好）记忆。分类的意义是采用不同写入、召回、冲突、过期和权限策略，而不是模仿人脑名词。

## 7. Memory、RAG、Session、State 和 Checkpoint 有什么区别？ `★★★★★`

### 标准回答

- Memory：跨时间复用的信息。
- RAG：当前问题所需的外部知识证据。
- Session：某段会话的消息连续性。
- State：当前 Run 的业务和控制状态。
- Checkpoint：为了暂停或失败恢复而保存的一致状态快照。

它们可能共用关系库或向量库，但语义和生命周期不同。尤其不能把保存全部消息称作长期 Memory，也不能把 Checkpoint 当经验记忆。

## 8. 长期 Memory 的写入、检索、更新和删除怎样设计？ `★★★★★`

### 标准回答

写入前评估未来效用、稳定性、来源、置信度、敏感度和主体范围。明确要求记住且合规的信息可保存；单次对话推断出的偏好不应直接成为高置信事实。

检索先按用户/租户/权限分区，再综合语义相关性、重要度、新鲜度、置信度和范围。更新使用版本和 Supersede（替代）关系解决冲突。删除要覆盖主数据库、向量索引、缓存和派生副本，并支持用户查看、纠正和删除。

## 9. 如何防止 Memory Pollution（记忆污染）？ `★★★★★`

### 标准回答

记忆写入使用 Schema Allowlist，只允许预定义类型；区分用户明确确认、工具事实和模型推断；保存来源、时间、置信度、作用域和版本。网页、邮件和 RAG 文档中的文字默认没有修改记忆或权限的指令权。

读取时仍重新做权限和策略校验。程序性记忆要先离线评测再发布；系统支持冲突检测、回滚、删除和异常写入告警。API Key、验证码等凭证不能进入普通 Memory。

## 10. 只用向量相似度召回 Memory 有什么问题？ `★★★★☆`

### 标准回答

语义相似不代表当前有效。向量召回可能取到过期偏好、其他任务信息或与当前事实冲突的记录。需要先做主体、租户和权限过滤，再结合时间衰减、重要度、置信度、作用域和冲突惩罚排序。

召回后还要去重、检查有效期、限制每类数量，并标明“已确认事实”还是“推断”。关系数据库适合保存真相、版本和权限，向量索引更适合候选召回。

## 11. 用户改变偏好时怎样解决记忆冲突？ `★★★★☆`

### 标准回答

一般优先级是：用户当前明确陈述 > 较新的明确陈述 > 权威工具事实 > 模型推断。新记录通过版本或 `supersedes` 指向旧记录，旧记录保留审计但不再默认召回。

不能简单追加两条矛盾记忆，也不应静默覆盖无法判断的事实。冲突无法自动裁决时应询问用户，并把“不确定”作为合法状态。

## 12. 如何评测 Agent Memory？ `★★★★☆`

### 标准回答

评估写入精确率/召回率、检索精确率/召回率、过期记忆命中率、冲突解决准确率、用户纠正成功率、删除完整性、跨租户泄露和对下游任务成功率的提升。

构造多会话测试：建立偏好、修改偏好、撤回、跨会话询问、无关干扰、恶意写入和过期信息。只测试“能否复述一句旧话”不能代表 Memory 机制有效。
