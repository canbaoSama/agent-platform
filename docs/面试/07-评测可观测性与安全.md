# Agent 评测、可观测性与安全高频面试题

> 返回：[AI Agent 面试题库](README.md)｜配套知识：[评测与可观测性](../知识体系/评测与可观测性.md)｜[安全与治理](../知识体系/安全与治理.md)

## 1. 如何系统评测一个 Agent？ `★★★★★`

### 标准回答

分五层：模型层评指令遵循和结构输出；组件层评 RAG、工具、Memory 和路由；轨迹层评步骤、禁止动作、重试和预算；Outcome（最终状态）层检查数据库、文件或 API 的真实结果；系统层评成功率、延迟、成本、安全和用户指标。

评分结合 Code-based、Model-based 和 Human Grader。相同 Task 运行多个 Trial，报告分布而非单次最好结果。能力集衡量能做到什么，回归集保护已经稳定的能力。

## 2. 为什么 Agent 最终答案正确仍可能判失败？ `★★★★★`

### 标准回答

它可能未经授权读取数据、调用禁止工具、重复产生副作用、碰巧猜对、超出预算，或只在文字中声称完成而真实环境未变化。因此既要评 Outcome，也要评关键过程约束。

例如订票 Agent 的最终答案写“预订成功”不能作为成功标准，应检查预订系统中的记录、金额、用户和幂等状态。

## 3. LLM-as-a-Judge 有哪些问题？如何校准？ `★★★★★`

### 标准回答

模型评分器存在位置偏差、长度/风格偏好、自我偏好、Prompt 敏感和事实盲区。它看不到的数据库状态无法靠语言判断，也可能被候选答案中的注入文本影响。

提供明确 Rubric、逐项评分和证据；随机候选顺序并隐藏方案身份；与代码规则组合；用人工标注集计算一致性、误判并周期校准。高风险结论不能只由一个模型评分器决定。

## 4. 如何构建 Agent 回归集？ `★★★★★`

### 标准回答

从产品要求、线上失败、用户反馈、人工 Trace 审查和红队测试提取真实样例，去敏后固定输入、环境和可验证成功标准。覆盖主路径、边界、工具错误、长任务、Memory 变化、越权和对抗输入。

每次修复把最小复现和相邻反例加入回归集；记录模型、Prompt、工具、知识和数据版本。按领域与风险切片报告，避免平均分掩盖严重问题。

## 5. Agent 变慢且工具经常失败，应该记录哪些可观测信息？ `★★★★★`

### 标准回答

Metrics 发现整体异常，Trace 定位某次请求的异常 Span，Logs 解释具体错误。统一 Trace ID 关联模型、RAG、工具、Handoff、Guardrail、Checkpoint 和最终 Outcome。

记录每步耗时、输入输出 Token、费用、候选与路由、工具参数摘要、状态、重试、错误码、模型/Prompt/工具/策略版本。模型输入输出可能含敏感数据，要脱敏、采样、分级授权并设置保留期限。

## 6. 线上 Agent 应监控哪些核心指标？ `★★★★★`

### 标准回答

- 质量：任务成功率、有据性、工具准确率、拒答与人工升级准确率。
- 可靠性：错误/超时、循环、重复副作用、重试与恢复成功率。
- 性能：P50/P95/P99、首 Token、工具和检索分阶段延迟。
- 成本：单成功任务 Token、费用、工具次数和并行宽度。
- 安全：越权、注入命中、敏感数据外发和审批绕过。

不能只看平均延迟和总请求成功率；Agent 的长尾失败与严重安全事件更关键。

## 7. 如何防御 Direct 和 Indirect Prompt Injection？ `★★★★★`

### 标准回答

Direct Injection 来自用户直接要求绕过规则；Indirect Injection 藏在网页、邮件、PDF、代码、RAG 或工具结果中。模型无法被保证始终正确区分自然语言数据与命令，因此 Prompt 提醒不是最终防线。

应把外部内容标记为不可信数据并与控制指令隔离；按任务缩小工具和数据范围；执行前由策略引擎按真实参数授权；高风险动作审批；工具沙箱、出站控制和最小权限；用对抗评测覆盖编码绕过和跨工具数据外泄。

## 8. Guardrail 应放在哪几层？ `★★★★★`

### 标准回答

Input Guardrail 检查用户输入；Output Guardrail 检查返回内容；Tool Guardrail 在每次调用前后校验工具、参数和结果；Runtime Guardrail 限制步数、Token、费用、网络和资源。

最重要的是副作用执行边界。安全组件异常、参数解析失败或策略不可用时，高风险动作应 Fail Closed（安全关闭），不能让模型自行判断继续。

## 9. 如何设计 Human-in-the-loop（人在回路）审批？ `★★★★☆`

### 标准回答

审批绑定具体动作、参数、目标、影响范围、依据和有效期，而不是模糊的“允许继续”。运行时在副作用前持久化 Checkpoint，展示可逆性与风险；记录审批者身份和决定；恢复时重新读取业务状态和权限，参数变化则重新审批。

按风险分层，避免所有操作都弹窗导致 Approval Fatigue（审批疲劳）。审批证明用户意图，不会赋予用户原本没有的权限。

## 10. 如何防止跨租户 RAG 或 Memory 数据泄露？ `★★★★★`

### 标准回答

租户过滤必须在存储查询和向量检索之前实施，服务端从认证上下文取得租户，不能信模型传入的 ID。高敏场景使用独立索引或数据库；共享索引则将租户和 ACL 作为强制过滤条件。

缓存键、Trace、评测数据、备份和派生摘要也必须包含租户边界。删除、撤权和权限变化要同步到索引与缓存。

## 11. 如何防止 Agent 读取私有数据后通过另一工具外传？ `★★★★★`

### 标准回答

这是 Data Exfiltration（数据外泄）和能力组合风险。对数据分级并记录来源；高敏数据只允许流向批准的模型、域名和工具；读取私有数据的 Agent 不默认拥有任意 HTTP、邮件或文件上传权限。

执行外发工具前做 DLP（数据防泄漏）和目标校验；使用网络 Egress Allowlist（出站允许列表）；最小化凭证与上下文；对异常“读取 → 外发”调用链告警和阻断。

## 12. 如何安全执行代码、Shell 或浏览器工具？ `★★★★★`

### 标准回答

运行在隔离沙箱或容器，使用临时工作区、非特权用户和最小文件挂载；限制网络域名、系统调用、CPU、内存、磁盘、进程数、时间和输出；密钥在执行端按需注入且不向模型展示。

高风险命令和不可逆动作审批；防止路径穿越、命令注入和 SSRF；任务结束销毁环境；保留脱敏审计和产物哈希。仅靠正则过滤命令无法覆盖所有绕过方式。

## 13. 如何发布 Agent 新版本并降低回归风险？ `★★★★☆`

### 标准回答

锁定模型、Prompt、工具、策略和知识版本，先跑组件与端到端回归；再用 Shadow（影子）流量比较但不产生副作用，随后 Canary（金丝雀）小流量发布。观察成功率、尾延迟、成本、安全和人工升级，设置自动回滚阈值。

涉及写操作时，影子环境必须隔离或替换为模拟工具。模型升级也应作为完整系统版本变更评测，而不是只比较单轮回答。
